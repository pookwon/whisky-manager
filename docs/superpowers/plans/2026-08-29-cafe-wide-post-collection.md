목록 DOM에서는 좋아요 수를 확인하지 못했다. 또한 당일이 아닌 글은 시각이 생략되고 조회 수가 축약될 수 있어 DOM만으로는 정확한 통계 원본이 되지 못한다. 구현은 이 화면이 내부적으로 호출하는 구조화된 목록 응답을 우선 사용하고 DOM은 계약 검증과 제한적 보강에 사용한다.

현재 점검에 사용한 브라우저 세션에서는 카페 가입 버튼이 보였고 일반 상세 글 본문이 렌더링되지 않았다. 따라서 아래 정보는 운영 회원 계정의 실제 Network 캡처 없이는 확정되지 않았다.

1. 페이지 화면이 내부적으로 호출하는 목록 API의 URL·파라미터·응답 계약
2. 원본 작성 시각의 날짜·시간·시간대와 수정 시각 필드
3. 좋아요 수의 목록/상세 API 필드 및 공개 범위
4. 작성자 버튼 ID가 실제 안정 member key인지 여부
5. 댓글 0건이 필드 0인지 필드/링크 부재인지
6. 비밀·운영진·Staff 게시판 글이 운영 계정의 전체글보기에 포함되는 범위
7. 삭제·이동·접근 제한 글의 응답 형태

739,554건은 50건 화면 기준으로도 약 14,792페이지다. 전수 클릭은 채택하지 않는다. 1차는 50건 목록 페이지에서 확인 가능한 값만 수집한다.

### 1차 제공 범위

1차 구현은 전체글보기의 구조화된 목록 응답만 사용하며 상세 글을 열지 않는다.

| 1차 수집 | 후속 상세 수집 |
|---|---|
| 카페 ID, 게시판 ID·이름, 글 ID | 본문과 본문 수정 이력 |
| 제목, 말머리, 공지 여부 | 좋아요 수 |
| 작성자 닉네임, 목록이 제공하는 작성자 ID | 정확한 작성 시각: 오늘 글만 시각, 하루 전부터 날짜만 표시됨 |
| 목록 표시 날짜/시각 | 첨부파일 메타데이터 |
| 조회 수, 댓글 수 | 상세 페이지에서만 확인되는 상태 |
| 최초/최근 관측 시각과 수집 실행 상태 | 댓글 작성자·댓글 본문 |

목록 응답이 제공하지 않는 값은 추측하거나 0으로 채우지 않고 null로 저장한다. 1차 완료 후 실제 데이터의 누락률과 통계 활용도를 확인한 다음 상세 수집을 별도 계획과 명시적 운영 상한으로 착수한다.

### 1차 검증 데이터 범위와 예상 부하

두 실행 범위를 구분한다. 날짜 경계는 모두 KST다.

| 구분 | 범위 | 목적 |
|---|---|---|
| 개발용 테스트 | 실행 시작 시 고정한 KST 앵커 기준 최근 완료된 3일 | 파서·DB·커서·중단 재개를 짧게 반복 검증 |
| 1차 스모크 테스트 | 2026-07-01 00:00 이상, 2026-08-01 00:00 미만 | 한 달 규모 백필, 처리 시간, 누락·중복, DB 증가량 확인 |

2026-08-29 전체글보기 화면에서 확인한 값은 다음과 같다.

- 페이지 크기 선택지: 5, 10, 15, 20, 30, 40, 50건
- 계획 기본값: 50건/페이지
- `page=N` 직접 접근 지원, 정렬은 최신 글 우선으로 고정
- 공지 숨김 지원; 실제 요청 파라미터는 raw 요청 캡처에서 확정
- 최신 150개 일반 글이 약 5시간 분량이어서 관측 시간대 게시 속도는 약 29건/시간
- 최신 글 ID와 7월 말 게시 글 ID 차이를 보조 지표로 사용하면 최근 평균은 약 450~550건/일로 추정

이 표본에 따른 1차 용량 추정은 다음과 같다. 실제 목록 API를 캡처한 뒤 첫 개발 실행의 실측값으로 다시 계산한다.

| 범위 | 예상 글 수 | 50건 기준 데이터 페이지 요청 | 예상 실행 시간 | 운영 예약 상한 |
|---|---:|---:|---:|---:|
| 최근 3일 | 1,350~1,650 | 본 수집 27~33페이지, 연속성 rewind 포함 약 54~66회 | 약 15~25분 | 30분 |
| 2026년 7월 본 수집 | 14,000~17,000 | 본 수집 280~340페이지, 연속성 rewind 포함 약 560~680회 | 약 3시간 30분~5시간 30분 | 6시간 |

7월 수집은 최신 페이지부터 8월 전체를 선형 통과하지 않는다. 전체글이 역시간순이고 `page=N` 접근을 지원하므로 다음 절차를 사용한다.

1. page 1의 `page_identity`를 fallback 기준값으로 저장한다.
2. page 1, 2, 4, 8… 순서의 지수 탐색으로 `2026-08-01 00:00 KST`를 앞뒤에서 끼우는 유효 page 구간을 찾는다.
3. 같은 실행 시작에 고정한 page 1 baseline과 요청 page의 identity·최신 timestamp 범위·페이지 그룹 정보를 비교해 silent fallback을 판정하고 유효 상한으로 사용한다. 서로 다른 캡처 사이의 identity 불일치는 새 글 유입으로 정상일 수 있으므로, fixture의 48/50 overlap은 현상 증거일 뿐 임계치 상수가 아니다.
4. 유효 구간 안에서 이진 탐색해 `2026-08-01 00:00 KST` 직전 글이 포함된 시작 페이지를 찾는다.
5. 그 페이지부터 페이지 번호를 증가시키며 오래된 방향으로 수집한다.
6. `posted_at < 2026-07-01 00:00 KST`인 글을 만난 페이지까지 저장하고 종료한다.
7. 경계 페이지에서는 범위 밖 글을 버리고 `2026-07-01 <= posted_at < 2026-08-01`만 저장한다.

이 절차는 목록 응답이 과거 글에도 정확한 작성 timestamp를 제공한다는 전제 위에 있다. 과거 글이 day 정밀도만 제공하면 같은 날짜 안에서 KST 자정 경계를 페이지 단위로 구분할 수 없으므로, 그 경우 경계 날짜(6월 30일, 8월 1일) 하루 전체를 보수적으로 수집한 뒤 저장 단계에서 `posted_date_kst`로 잘라낸다. timestamp 정밀도 확인은 Phase 0의 완료 조건이며 이진 탐색 구현의 전제 조건이다.

전체 글 수로 계산한 이론상 페이지 수는 실제 허용 page 상한이 아니다. `page=14795` 표본은 page 1로 silent fallback했다. 7월 시작점은 page 300 부근에서 확인됐으므로 지수 탐색과 구간 이진 탐색은 약 18~22회로 예상한다. 데이터 완전성을 우선해 이전 anchor가 다음 페이지에 직접 보이지 않으면 `totalArticleCount`가 같아도 직전 페이지를 rewind 검증하므로 안정 상태에서도 본 수집 요청은 페이지 수의 약 2배가 된다. 따라서 7월 스모크의 총 조회는 탐색 18~22회와 본 수집·rewind 약 560~680회를 합쳐 약 578~702회다. 운영 예약 상한은 6시간으로 잡고, 3일 실측 p95와 실제 휴지 합계로 다시 계산한다.

개발용 “최근 완료된 3일”은 실행 시작 순간에 KST 앵커를 고정한다. 예를 들어 2026-08-29에 시작하면 `2026-08-26 00:00 <= posted_at < 2026-08-29 00:00 KST`이며, 실행 중 자정이 지나도 범위를 바꾸지 않는다.

전체글 백필은 기존 가입인사 일일 수집보다 훨씬 많은 페이지를 읽으므로 더 보수적인 전용 간격을 사용한다.

- 페이지 요청 사이: 무작위 5~9초
- 20페이지마다: 무작위 2~5분 휴지
- 100페이지마다: 추가 10~20분 장기 휴지
- 첫 페이지 전에는 지연하지 않고 마지막 페이지 뒤에는 불필요한 지연을 두지 않음
- HTTP 429, 접근 제한, 로그인/권한 이상, 연속 5xx가 보이면 즉시 중단
- 일시 네트워크 오류는 최대 3회 지수 backoff 후 실행을 partial/failed로 종료

예상 시간은 위 지연과 페이지당 응답·파싱·DB 저장 0.3~1.0초를 반영한 범위다. 실행마다 지연값을 새로 뽑되 테스트에서는 주입한 난수와 시계로 결정적으로 검증한다. 로그인 확인, 메뉴 메타데이터 확인 등 실행당 고정 요청은 데이터 페이지 요청과 별도로 1~3회 이내를 목표로 한다.

여기서 “조회 횟수”는 게시글 목록 데이터 요청 수다. 브라우저 화면을 직접 렌더링하면 JS·CSS·이미지·광고·텔레메트리 같은 부수 리소스 요청이 추가되므로 1차 수집은 화면 페이지 이동이 아니라 기존 Chrome 세션 안의 목록 API 호출을 사용한다. 실제 Network 캡처에서 한 페이지 이동이 목록 API를 둘 이상 호출한다면 위 요청 수와 시간 추정을 그 배수로 즉시 보정한다.

각 실행은 다음 실측값을 `collection_runs`에 기록한다.

- 요청 페이지 수, 수집/신규/갱신/중복 글 수
- 시작·종료·총 소요 시간과 페이지 응답 시간의 최소/평균/p95/최대
- 실제 페이지 간 지연의 최소/평균/최대
- 재시도·HTTP 오류·파서 오류 수
- 실행 전후 PostgreSQL 테이블·인덱스 크기와 게시글/관측 행 증가량

개발용 3일 실행 결과가 아래 조건을 만족해야 7월 스모크 테스트로 진행한다.

1. 동일 범위 재실행 시 게시글 중복 행이 0건이다.
2. 페이지 반복·누락 신호가 없고 시작/종료 날짜가 KST 범위와 맞는다.
3. HTTP/파서 오류가 0건이거나 원인이 설명되고 안전하게 재개된다.
4. 실측 p95 응답 시간과 실제 휴지 합계를 반영해 7월 예상 시간이 6시간 예약 상한 안에 든다.
5. 실행 중단 후 anchor 글 기준으로 재개되고, rewind 연속성 검증(4.4절)에서 간극이 0건이거나 간극이 감지되어 재수집된다.

## 1. 목표와 성공 조건

전체 목표는 수집 대상 게시판의 글 제목, 말머리, 작성자, 작성 시각, 조회 수, 좋아요 수, 댓글 수와 향후 본문을 내부 DB에 누적하는 것이다. 1차는 목록에서 확인 가능한 제목·말머리·작성자·작성일·조회 수·댓글 수까지만 수집한다. 이후 다음 질문을 원본 재수집 없이 답할 수 있는 형태를 만든다.

- 게시판·말머리·작성자·요일·시간대별 글 수
- 게시 후 1일/7일 동안의 조회·좋아요·댓글 증가량
- 조회 대비 좋아요/댓글 비율과 반응이 빠른 글
- 기간별 활성 작성자 수와 신규/재방문 작성자 비율
- 수집 누락, 파서 변경, 특정 게시판 접근 실패 여부

성공 조건은 다음과 같다.

1. 같은 글을 반복 수집해도 게시글이 중복되지 않는다.
2. 수집 진행 중 피드가 이동해 글이 건너뛰어지는 간극이 감지되지 않은 채 지나가지 않는다.
3. 바뀌는 카운터를 덮어쓰지 않고 관측 이력을 남긴다.
4. 부분 실패가 전체 실행의 성공으로 숨겨지지 않는다(run 상태 partial/failed로 드러난다).
5. 중단 후 재시작해도 마지막 확정 지점부터 이어진다.
6. 모든 사용자 표시와 날짜 경계는 KST를 사용하되 PostgreSQL 시각은 `timestamptz`로 저장한다.
7. 기존 가입인사 자동화의 `COLLECT` 흐름과 쓰기 동작에 회귀가 없다.

## 2. 현재 구조 점검

현재 구현에는 재사용할 기반이 있다.

- 네이버 요청은 Chrome 확장 안에서 `credentials: include`로 수행하므로 쿠키를 앱 밖으로 꺼내지 않는다.
- 확장과 데스크톱 앱 사이에 요청/응답 프로토콜, 진행 이벤트, 타임아웃이 있다.
- 목록 페이지를 페이지 단위로 읽고 중복 ID와 정지 조건을 검사하는 수집 루프가 있다.
- 기존 앱 상태는 better-sqlite3 + Drizzle로 유지하며, 게시글 수집 데이터에는 별도 PostgreSQL 연결과 Drizzle PostgreSQL 스키마를 추가한다.

하지만 `COLLECT` 메시지 자체는 `automationId`를 받는 범용 계약이어도, 그 구현체(`cafeClient`의 수집 walk)와 `RawCandidate`는 가입인사 메모 게시판의 memo API, 본문 기반 판정, `sincePostedAt` 기준 다중 페이지 walk에 결합되어 있다. `RawCandidate`는 자동화 판정에 필요한 본문과 댓글 수 중심이고, 일반 게시판의 제목·말머리·조회·좋아요를 표현하지 못한다. 또한 자동화 설정에는 기능별 `boardId` 하나만 있어 “전체 게시판 목록”의 원천이 없다.

따라서 기존 타입을 억지로 확장하지 않고 다음 경계를 새로 둔다.

```text
Chrome 확장
  게시판 발견 → 일반 글 목록 읽기/파싱 → 수집 응답
       ↓ localhost WebSocket
데스크톱 수집 서비스
  실행 계획 → 페이지 단위 요청 → 검증 → 트랜잭션 저장 → 커서 확정
       ↓
PostgreSQL
  게시판 / 게시글 현재값 / 지표 관측값 / 실행·커서
```

기존 SQLite는 가입인사 실행, 설정, 템플릿, 페어링 토큰 등 현재 앱의 로컬 상태만 계속 소유한다. 게시글 수집 테이블을 SQLite와 PostgreSQL에 이중으로 만들지 않는다. PostgreSQL 연결 또는 트랜잭션이 실패하면 해당 페이지를 저장하지 않고 `collection_feed_state`도 전진시키지 않으며, 연결 복구 후 같은 페이지를 다시 읽는다.

### PostgreSQL 배치 전략: 로컬에서 시작해 온라인으로 이전

1차 개발·3일 테스트·2026년 7월 스모크는 로컬 PostgreSQL 서버에서 수행한다. 이후 여러 PC 공유, 원격 대시보드, 중앙 백업이 필요해지는 시점에 관리형 PostgreSQL로 이전한다.

애플리케이션 코드는 로컬/온라인을 구분하지 않는다.

- 연결은 `DATABASE_URL`과 TLS 관련 설정으로만 주입하고 `localhost`를 코드에 박지 않는다.
- Drizzle PostgreSQL schema와 migration은 하나만 유지한다.
- 로컬과 온라인은 가능한 한 같은 PostgreSQL major version을 사용한다.
- 특정 관리형 서비스에만 있는 타입·함수·확장에 의존하지 않는다.
- `pg_trgm` 등 extension은 로컬과 이전 대상 양쪽에서 사용 가능함을 확인한 뒤 migration에 넣는다.
- 수집 계정, migration 계정, 읽기 전용 분석 계정을 분리한다.

로컬 PostgreSQL은 앱에 바이너리로 포함하거나 Electron이 자동 설치하지 않는다. 개발 환경에서는 고정 버전 컨테이너 또는 명시적으로 설치된 로컬 서버를 사용하고, 앱은 연결 실패를 안내할 뿐 서버 프로세스를 임의로 시작·종료하지 않는다.

온라인 이전 절차는 다음과 같다.

1. 로컬과 대상 서버의 PostgreSQL major version·extension·collation·timezone을 확인한다.
2. 대상 빈 DB에 동일한 Drizzle migration을 먼저 적용한다.
3. 수집기를 페이지 경계에서 일시 정지하고 마지막 커밋 anchor를 기록한다.
4. `pg_dump -Fc` custom-format으로 일관된 논리 백업을 만든다. role/owner/ACL은 환경별로 다르므로 데이터·schema와 분리해 다룬다.
5. 대상 DB에 `pg_restore`하고 sequence/identity, constraint, index 상태를 확인한다.
6. 테이블별 행 수, min/max 글 ID·작성일, 최근 커서, 표본 hash, orphan FK를 비교한다.
7. 대상 DB를 읽기 전용 검증한 뒤 `DATABASE_URL`을 전환한다.
8. 동일 페이지 멱등 재실행으로 전환 경계 누락이 없음을 확인하고 수집을 재개한다.
9. 로컬 DB는 즉시 삭제하지 않고 일정 기간 읽기 전용 rollback 자료로 보관한다.

현재 예상 데이터 규모에서는 짧은 계획 중단을 둔 dump/restore가 가장 단순하다. 이전 중에도 무중단 쓰기가 반드시 필요해질 때만 logical replication/CDC를 별도 설계한다. 파일 시스템 수준 PostgreSQL 데이터 디렉터리 복사는 major version과 운영 환경 의존성이 크므로 이전 수단으로 사용하지 않는다.

## 3. 선행 조사: 실제 응답 계약 확정

확인된 API 주소·클라이언트 변환 필드·남은 fixture 항목은 [`2026-08-30-cafe-article-list-contract.md`](../specs/2026-08-30-cafe-article-list-contract.md)에 기록한다. 현재 일반 글 API, 공지 분리, 50건 페이지, 작성자 memberKey, timestamp·게시판·조회·댓글 raw 필드 후보까지 확인됐다.

일반 게시판 엔드포인트는 비공개·변경 가능 API이므로 구현 전에 로그인된 운영 Chrome의 DevTools Network에서 다음을 캡처한다.

1. 카페 메뉴/게시판 목록 요청과 응답
2. 일반 게시판 첫 페이지와 다음 페이지 요청
3. 말머리 있음/없음, 공지, 삭제 글, 비밀 글, 댓글 0건, 좋아요 0건 사례
4. 조회·좋아요·댓글 수가 목록 응답에 모두 있는지
5. 전체글 보기와 게시판별 목록의 페이지네이션/정렬 안정성
6. 접근 권한이 없는 게시판, 메모 게시판, 상품/캘린더 등 특수 게시판의 구분 값

캡처 결과는 개인정보와 쿠키를 제거한 fixture로 저장하고 파서는 fixture만으로 테스트한다. 실계정 반복 E2E는 만들지 않는다.

이 단계에서 다음을 결정한다.

- 가능하면 구조화된 JSON 목록 엔드포인트를 사용한다.
- 1차 수집원은 `menuId=0` 전체글보기 단일 피드로 고정한다. 게시판별 순회는 1차 대안이 아니다.
- 목록 응답에서 게시판 ID·이름을 얻지 못하면 DOM 행에서 보강하거나 null로 저장하며, 그 이유로 게시판별 순회로 전환하지 않는다.
- 목록에 없는 필드를 위해 모든 상세 글을 추가 조회하지 않는다. 비용이 큰 상세 조회는 명시적인 2단계 기능으로 남긴다.

## 4. 데이터 모델

### 4.1 `cafe_boards`

게시판 발견 결과와 수집 정책을 보관한다.

| 열 | 의미 |
|---|---|
| `cafe_id`, `board_id` | 복합 기본 키 |
| `name` | 게시판 표시 이름 |
| `kind` | normal, memo, special, unknown |
| `collect_enabled` | 운영자가 제외할 수 있는 플래그 |
| `discovered_at`, `last_seen_at` | 최초/최근 발견 시각 |
| `retired_at` | 메뉴에서 사라진 시각; 즉시 삭제하지 않음 |

### 4.2 `cafe_posts`

글의 현재 메타데이터와 최초/최근 관측 상태를 한 행으로 유지한다.

| 열 | 의미 |
|---|---|
| `cafe_id`, `post_id` | 복합 기본 키. 글 번호는 카페 단위로 유일하다고 검증 후 사용 |
| `board_id` | 최근 관측 게시판; 이동 가능성을 고려해 PK에 넣지 않음 |
| `title`, `prefix` | 글 제목과 말머리, 읽을 수 없으면 null |
| `author_nickname`, `author_id` | 표시명과 안정 식별자. 식별자를 못 얻으면 null |
| `posted_date_kst` | 목록에 표시된 KST 날짜 `YYYY-MM-DD`; 기간 필터의 1차 기준 |
| `posted_at` | raw 응답이 정확한 시각을 줄 때만 `timestamptz`, 아니면 null |
| `posted_precision` | day 또는 minute/millisecond; 표시값의 정밀도 기록 |
| `first_seen_at`, `last_seen_at` | 수집기가 처음/마지막으로 본 `timestamptz` |
| `last_observed_run_id` | 마지막으로 확인한 실행 |
| `unavailable_at` | 삭제/권한 변경 추정 시각. 한 번 안 보였다고 즉시 설정하지 않음 |

추천 인덱스:

- `(cafe_id, board_id, posted_date_kst)` — 게시판·기간 집계 및 증분 탐색
- `(cafe_id, author_id, posted_date_kst)` — 작성자 활동 집계
- `(cafe_id, prefix, posted_date_kst)` — 말머리별 집계

화면 DOM만 사용할 경우 오늘 글의 `HH:mm`은 수집 시점의 KST 날짜와 결합해 minute 정밀도로 저장하고, 하루 전부터 보이는 날짜 전용 값은 `posted_date_kst`만 저장하며 `posted_at=null`, `posted_precision=day`로 둔다. 자정을 임의 시각으로 채워 정확한 작성 시각처럼 만들지 않는다. raw 목록 응답에 원본 timestamp가 있으면 `posted_at`과 정밀도를 올리되 화면값과 일치하는지 fixture로 검증한다.

### 4.3 `post_metric_observations`

변하는 값은 게시글 행에만 덮어쓰지 않고 관측 이력으로 남긴다.

| 열 | 의미 |
|---|---|
| `id` | 내부 정수 키 |
| `cafe_id`, `post_id` | 대상 글 |
| `observed_at` | 관측 시각(`timestamptz`) |
| `view_count`, `like_count`, `comment_count` | 각 값; 읽지 못한 값은 0이 아니라 null |
| `collection_run_id` | 값을 만든 실행 |
| `source` | list 또는 detail. 동일 필드가 다르면 detail을 우선 |
| `parser_version` | 어떤 응답 계약/파서가 값을 만들었는지 식별 |

인덱스/제약:

- unique `(collection_run_id, cafe_id, post_id, source)`
- index `(cafe_id, post_id, observed_at)`
- index `(observed_at)`은 전체 기간별 스냅샷 분석이 실제로 필요할 때 추가

한 실행에서 목록 관측과 상세 관측은 별도 행이 될 수 있다. 분석 조회는 동일 실행·글·필드에 detail 값이 있으면 이를 우선하고, 없으면 list 값을 사용한다. `observed_at`만으로 중복을 판정하지 않아 같은 millisecond에 두 출처가 들어와도 충돌하지 않게 한다.

같은 실행이 같은 글을 두 번 목록 관측하는 경우가 정상적으로 존재한다 — 커밋 페이지 재읽기(rewind 연속성 검증), 페이지 이동으로 같은 글이 두 페이지에 나타나는 경우다. 이때 관측 삽입은 `ON CONFLICT DO NOTHING`으로 첫 관측을 유지한다. 이진 탐색·재위치용 프로브 페이지의 응답은 관측값으로 저장하지 않는다(수집 대상 확정 전의 위치 확인일 뿐이다).

`observed_at`은 데스크톱이 기록한 해당 페이지 fetch 시작 시각으로 정의한다. fetch 완료와 트랜잭션 커밋 시각은 run 통계에만 남긴다. 확장이 보내는 시각을 신뢰 원천으로 쓰지 않는다.

초기 구현은 성공적으로 다시 읽은 글마다 관측값을 저장한다. 데이터 증가가 확인되면 “직전 값과 모두 같으면 저장 생략” 정책을 적용할 수 있지만, 그 경우 관측 공백과 값 미변화를 구분할 수 있도록 `last_seen_at`은 반드시 갱신한다.

### 4.4 `collection_runs`와 `collection_feed_state`

1차 수집원은 게시판별 목록이 아니라 `menuId=0` 전체글보기 단일 피드로 고정한다. 피드의 identity는 `(cafe_id, feed_kind, menu_id)`이며 이 조합에 unique 제약을 둔다. `size`, 공지 숨김 여부, 대상 시작/종료 시각, 커서, 마지막 성공 실행, `stop_reason`은 identity가 아니라 상태다. `collection_runs`에는 feed당 `status='running'`인 행이 하나만 존재하도록 partial unique index 또는 동등한 DB 제약을 둔다. `last_run_id`류 참조는 `collection_runs` FK로 선언하고, `target_start_ms < target_end_ms`, 페이지 번호 ≥ 1, 카운터 ≥ 0 같은 불변식은 애플리케이션 검증에만 맡기지 않고 DB check 제약으로도 선언한다. 글 행의 `board_id`는 분류 데이터이지 페이지네이션 커서의 소유 단위가 아니다.

`collection_runs`에는 최소한 다음을 남긴다.

- `run_kind`(development/backfill/incremental), `feed_kind`, `target_start_ms`, `target_end_ms`
- 시작/종료 시각, 상태(running/succeeded/partial/failed/interrupted), `stop_reason`
- 탐색/본 수집/실제 요청 페이지 수
- 관측/범위 내/삽입/갱신/중복/실패 글 수
- 페이지 응답 시간 min/avg/p95/max와 실제 지연 min/avg/max
- 실행 전후 PostgreSQL 테이블·인덱스 크기, 마지막 커밋 anchor와 참고 페이지 번호

#### anchor 기반 커서와 이동 감지

역시간순 피드는 수집 중에도 새 글이 위에 쌓여 과거 글의 페이지 번호가 계속 이동한다(관측치 약 29건/시간). 따라서 페이지 번호는 위치의 참고값일 뿐 커서의 신뢰 원천이 아니다. 커서의 신뢰 원천은 **anchor 글 ID** — 마지막으로 커밋한 페이지에서 가장 오래된 일반 글의 ID다.

커서는 페이지를 읽을 때마다 전진시키지 않는다. 해당 페이지의 DB 트랜잭션이 커밋된 뒤에만 확정해 중단 시 누락을 막는다. 커밋 시 `collection_feed_state`에 함께 기록하는 값:

- anchor 글 ID와 그 `posted_date_kst`(anchor 소실 시 fallback용)
- 커밋 페이지의 첫/마지막 일반 글 ID와 `page_identity`(정렬된 일반 글 ID 목록의 해시; 계산 규칙은 Phase 0 산출물)
- 참고용 페이지 번호

**연속 진행 시 간극 감지.** 안정 상태의 인접 페이지는 공통 글 ID가 없는 것이 정상이므로 "다음 페이지가 직전과 겹치는가"는 연속성의 불변식이 될 수 없다. 대신 다음 페이지를 요청할 때 **의도적으로 한 페이지 rewind**해 직전 커밋 페이지의 tail을 다시 읽고, ID 중복 제거로 이어붙인다. rewind한 페이지에 직전 anchor가 나타나면 연속이 확인된 것이고(중복 저장은 멱등 upsert와 관측 `DO NOTHING`으로 무해), 나타나지 않으면 피드가 이동한 것이므로 anchor 재탐색으로 전환한다. `page_identity`가 직전 커밋과 완전히 같으면 반복 페이지 오류로 중단한다.

**중단 후 재개.** 저장된 페이지 번호는 중단 시간이 길수록 다른 내용을 가리키므로 신뢰하지 않는다. 재개 시 anchor 글 ID가 현재 어느 페이지에 있는지 이진 탐색으로 재위치한 뒤 그 글 다음부터 이어간다. anchor 글이 삭제·이동되어 찾을 수 없으면 함께 저장한 첫/마지막 글 ID와 `posted_date_kst` 범위로 재위치를 시도하고, 그래도 실패하면 대상 범위 경계에서 보수적으로 rewind해 멱등 재수집한다.

페이지네이션과 영속 상태의 소유자는 데스크톱 수집 서비스 하나로 고정한다. 확장은 한 요청에서 지정된 `page` 하나만 50건으로 읽고 `items`, `page`, `has_more`, `page_identity`를 반환한다. 확장은 커서를 저장하거나 다음 페이지를 스스로 요청하지 않는다.

커서 갱신은 행 잠금만으로 끝내지 않고 compare-and-set으로 수행한다. 페이지를 요청하기 전에 읽은 `state_version`과 `anchor_post_id`를 expected 값으로 들고, 커밋 시 `UPDATE collection_feed_state ... WHERE state_version = expected_version AND anchor_post_id IS NOT DISTINCT FROM expected_anchor`로 갱신한다. 성공 시 `state_version`을 1 올린다. 갱신 행이 0이면 다른 실행이 먼저 전진한 것이므로 해당 트랜잭션을 롤백하고 새 상태에서 재위치한다. 이 규칙이 게시글 upsert·관측 삽입·anchor 확정을 한 트랜잭션으로 묶는 이유다.

#### 종료·취소 상태 기계

취소와 종료는 페이지 경계에서만 의미를 확정한다.

| 중단 시점 | 처리 |
|---|---|
| 페이지 fetch 진행 중 | 응답을 기다리지 않고 폐기, 커서 불변, run은 `interrupted` |
| 응답 수신 후 커밋 전 | 페이지 폐기, 커서 불변, run은 `interrupted`; 재개 시 같은 페이지 재읽기 |
| 커밋 완료 후 | 커서 확정 상태로 run 종료(`interrupted` 또는 정상 종결) |
| backoff·휴지 대기 중 | 대기를 즉시 끝내고 run 종결 |

`ABORT`는 requestId만이 아니라 수집 run ID를 함께 지정하고, 데스크톱은 취소 처리 결과(마지막 커밋 anchor)를 run에 기록한다. 앱 정상 종료 시에도 같은 규칙을 따르며, 비정상 종료로 `running`으로 남은 run은 다음 시작 때 `interrupted`로 정리한다.

### 4.5 `post_detail_tasks` — 후속 상세 수집에서 추가

1차 마이그레이션에는 포함하지 않는다. 후속 단계에서 목록 저장과 실제 탐색의 수명주기가 다르므로 상세 보강은 전용 영속 큐로 관리한다.

| 열 | 의미 |
|---|---|
| `id` | 내부 작업 ID |
| `cafe_id`, `post_id` | 대상 글 |
| `requested_fields` | 보강할 필드 목록 JSON |
| `status` | pending, running, succeeded, retry_wait, failed, cancelled |
| `priority` | 새 글·표본 검증 등 처리 우선순위 |
| `attempts`, `next_attempt_at` | 재시도 횟수와 다음 가능 시각 |
| `locked_by_run_id`, `locked_at` | 실행 중 소유권과 중단 복구 정보 |
| `last_error`, `last_diagnostic` | 정제된 오류 정보 |
| `created_at`, `updated_at`, `completed_at` | 작업 수명주기 |

unique `(cafe_id, post_id, requested_fields)`로 같은 보강 작업의 무한 중복 생성을 막되, `requested_fields`는 필드명을 정렬하고 중복을 제거한 canonical JSON으로 저장한다. 성공 작업을 언제 다시 만들지는 지표 재관측 정책이 결정한다. 앱 시작 시 `running`인데 소유 run이 중단된 작업은 `retry_wait`로 되돌린다. 기존 `ExecutionStatus`는 자동화 공용 타입이지만 승인 대기·댓글 실행의 수명주기를 표현하는 의미이므로, 상세 수집 작업에는 재사용하지 않고 위 상태 집합을 별도로 둔다.

### 4.6 의도적으로 보류하는 테이블

- 글 본문 및 댓글: 향후 수집 대상이지만 개인정보·저장량·상세 요청 부하를 별도 검증해야 하므로 1차 목록 수집에서는 보류한다.
- 일/주 집계 테이블: 원본 관측값으로 먼저 쿼리하고 성능 문제가 측정된 뒤 추가한다.
- 제목/말머리 변경 이력: 현재값은 보존하되 변경 이력의 분석 요구가 생길 때 `post_metadata_history`를 추가한다.
- 원본 응답 영구 저장: fixture는 개발 자료로 최소화하고 운영 DB에는 기본 저장하지 않는다.

### 4.7 전체 본문 저장까지 고려한 PostgreSQL 용량 검토

PostgreSQL은 약 74만 건의 게시글 본문과 장기 관측 이력을 충분히 처리할 수 있다. 큰 TEXT 값은 PostgreSQL의 TOAST 저장 메커니즘 대상이 되며, 대량 초기 적재에는 `COPY`, 반복 수집에는 `INSERT ... ON CONFLICT`가 적합하다. 1차 페이지가 50건이므로 실시간 수집 경로에서는 복합키 upsert가 충분하고, 전체 이관·복구 도구에서만 `COPY`를 사용한다.

본문의 UTF-8 평균 크기를 아직 모르므로 범위로 계산한다. 아래는 739,554건 전체를 저장할 때 본문 원문만의 단순 곱이며 PostgreSQL 행·TOAST·인덱스 비용은 포함하지 않았다.

| 평균 본문 크기 | 본문 원문 합계 |
|---:|---:|
| 2KB | 약 1.5GB |
| 5KB | 약 3.7GB |
| 10KB | 약 7.4GB |
| 20KB | 약 14.8GB |

게시글 메타데이터, TOAST, B-tree 인덱스, 관측 이력으로 원문 합계보다 커진다. GIN 전문 검색 인덱스를 추가하면 토큰과 언어 설정에 따라 저장량과 쓰기 비용이 크게 늘 수 있다. 따라서 전체 운영 DB는 평균 본문 5KB일 때 대략 6~10GB, 평균 10KB일 때 대략 11~20GB를 최초 용량 계획값으로 사용한다. 이는 추정치이며 3일과 7월 표본의 실제 UTF-8 byte 합계와 `pg_total_relation_size`로 다시 계산한다.

본문을 추가할 때 `cafe_posts`에 직접 넣지 않고 같은 PostgreSQL 데이터베이스의 별도 `post_contents` 테이블을 사용한다.

| 열 | 의미 |
|---|---|
| `cafe_id`, `post_id` | 복합 기본/외래 키 |
| `body_text` | 분석·검색용 정규화 평문 |
| `body_html` | 필요한 경우에만 원본 구조 보존; 기본은 null |
| `content_hash` | 같은 내용의 불필요한 재저장 방지 |
| `content_bytes` | UTF-8 실제 크기 측정 |
| `fetched_at`, `updated_at` | 수집·변경 시각 |
| `parser_version` | 본문 파서 계약 버전 |

본문 수정 이력이 실제 분석 요구가 되면 현재 본문과 `post_content_versions`를 분리한다. 첨부 이미지·동영상 파일 바이너리는 PostgreSQL에 넣지 않고 URL, MIME type, 크기, 상태 같은 메타데이터만 별도 테이블에 저장한다.

전문 검색은 본문을 저장한 직후 자동 도입하지 않는다. PostgreSQL `tsvector` + GIN은 지원되지만 기본 언어 설정만으로 한국어 형태소 검색 품질을 보장할 수 없다. 초기에는 정확 일치와 필요 시 `pg_trgm` 기반 부분 문자열 검색을 검토하고, 형태소 검색 요구가 확정되면 전용 분석기 또는 검색엔진을 별도 결정한다.

PostgreSQL 운영에는 다음 장치를 둔다.

- Electron main process에서만 사용하는 최소 권한 수집 전용 DB 계정
- 비밀번호를 소스·SQLite 설정·내보내기 파일에 저장하지 않고 OS 안전 저장소 또는 환경별 secret로 주입
- 연결/statement/idle transaction timeout 설정; TLS는 온라인 이전 시 필수, 로컬 서버는 지원할 때만 활성화
- 작은 connection pool과 페이지 단위 짧은 트랜잭션; 전체 백필을 한 트랜잭션으로 묶지 않음
- DB 연결 실패 시 페이지 커서 미전진, 동일 페이지 멱등 재시도
- 관리형 PostgreSQL의 자동 백업과 point-in-time recovery 또는 동등한 자체 백업 정책
- `pg_total_relation_size` 기반 테이블·인덱스 용량 경고
- autovacuum 상태, dead tuples, connection 수, 장기 트랜잭션 모니터링
- 대형 인덱스는 운영 수집을 오래 막지 않도록 `CREATE INDEX CONCURRENTLY` 검토
- 마이그레이션은 staging 복제본에서 실행 시간과 lock을 먼저 검증

50건 페이지별 upsert와 관측 삽입은 한 PostgreSQL 트랜잭션으로 묶는다. 통계 집계, GIN 인덱스 생성, 전체 재색인처럼 긴 작업은 수집 트랜잭션과 분리한다. `post_metric_observations`가 수천만 행으로 커지고 기간별 보관/삭제가 필요해질 때 월 단위 partition을 검토하며, 74만 게시글만으로는 선제 partition하지 않는다.

3일 개발 수집과 7월 스모크에서 다음 용량 측정을 추가한다.

- 행당 메타데이터 평균/p50/p95 byte
- 본문 도입 전에는 표본 상세 글의 `body_text` byte만 읽기 전용으로 측정하고 영구 저장하지 않음
- `pg_table_size`, `pg_indexes_size`, `pg_total_relation_size` 측정
- 74만 건 환산 DB 크기, GIN 미사용/사용 두 시나리오
- 백업 복원, 마이그레이션, 앱 재연결에 걸리는 시간

PostgreSQL은 게시글 수집과 분석의 단일 원본이다. 기존 SQLite에는 이 테이블들의 복제본을 두지 않는다. PostgreSQL 장애 동안 새 페이지를 임시 저장하지 않고 안전하게 멈춘 뒤 같은 페이지에서 재개한다. 오프라인 수집 요구가 실제로 생길 때만 별도 outbox를 설계한다.

## 5. 수집 전략

### 1차 수집 방식: 전체글 목록 요청만 사용

1차는 `BoardPageReader`와 목록 저장까지만 구현한다. `PostDetailNavigator`, 실제 링크 클릭, `post_detail_tasks`는 Phase 6 이후 별도 계획의 범위이며 아래 내용은 구현 지시가 아니라 후속 설계를 위한 참고다.

기본 방식은 로그인된 Chrome 세션에서 게시판 목록이 사용하는 실제 요청을 재현하는 것이다. 다만 목록 응답만으로 얻을 수 없거나 페이지 JavaScript 실행이 필요한 값은 실제 페이지 탐색으로 보완한다.

두 경로의 책임을 다음처럼 고정한다.

| 경로 | 용도 | 기본 여부 |
|---|---|---|
| 목록 요청 | 게시판 발견, 글 ID, 제목, 말머리, 작성자, 작성 시각, 목록에 노출된 카운터 수집 | 기본 |
| 실제 탐색 | 목록에 없는 좋아요 수 등 상세값, 페이지 실행이 필요한 값, 표본 검증 | 조건부 |

실제 탐색은 단순히 상세 URL을 `fetch`하는 것이 아니라 Chrome 탭의 페이지 문맥에서 다음 순서로 동작한다.

```text
수집 전용 탭 준비
→ 게시판 목록 화면 로드 및 준비 상태 확인
→ 대상 글 링크를 DOM에서 식별
→ 화면에 없으면 자연스러운 단위로 스크롤
→ 링크의 click() 실행
→ URL·DOM·필수 필드가 준비될 때까지 제한 시간 내 대기
→ 렌더링된 상세값 읽기
→ 목록으로 돌아가기 또는 다음 안전한 URL로 이동
→ 임의 지연 후 다음 대상 처리
```

이 방식은 사람이 사용하는 것과 같은 페이지 전환 및 JavaScript 실행 효과를 만들지만, 사람과 완전히 동일하거나 탐지 불가능함을 목표로 삼지 않는다. 마우스 궤적을 꾸미거나 브라우저 신호를 위조하지 않는다. 핵심은 정상 UI가 수행하는 요청과 상태 전이를 따르고 카페에 과도한 부하를 주지 않는 것이다.

#### 실제 탐색을 사용하는 조건

다음 중 하나일 때만 상세 탐색 작업을 만든다.

1. 목표 필드가 목록 응답에 존재하지 않는다.
2. 목록 값이 축약되거나 신뢰할 수 없어 정확한 값이 필요하다.
3. 페이지 JavaScript가 실행돼야 값 또는 상태가 만들어진다.
4. 파서 정확도를 확인하기 위한 제한된 표본 검증이다.

목록에서 이미 정확하게 얻은 필드를 확인하려고 모든 글을 열지 않는다. 동일 글의 동일 필드는 같은 실행에서 한 번만 상세 탐색한다.

#### 탭 격리

- 운영자가 보고 있는 활성 탭을 빼앗지 않는다.
- Chrome 확장이 이름을 붙여 관리하는 수집 전용 비활성 탭 하나를 재사용한다.
- 새 창을 반복 생성하지 않으며 수집 종료 후 정책에 따라 탭을 닫거나 다음 실행까지 유지한다.
- 사용자가 전용 탭을 닫거나 이동시킨 경우 이를 감지해 안전하게 다시 만들거나 실행을 중단한다.
- 로그인·권한 확인 페이지, 예상하지 못한 외부 도메인, 파일 다운로드로 이동하면 즉시 중단한다.

백그라운드 탭에서 네이버가 렌더링 또는 타이머를 제한하는지 Phase 0에서 검증한다. 제한된다면 전용 창을 최소화 상태로 유지하는 방안을 검토하되, 운영자의 활성 창을 자동 전환하지 않는다.

#### 사람과 유사한 처리 속도

- 게시판 페이지와 상세 페이지가 실제로 준비된 뒤 다음 동작을 수행한다.
- 요청/클릭 간격은 설정 범위에서 흔들고, 페이지 로딩 시간도 간격에 포함한다.
- 게시판 전환 또는 일정 건수 처리 후 긴 휴지 구간을 둔다.
- 시간당·일별 상세 탐색 상한을 둔다.
- 429, 접근 제한, 추가 인증, 비정상 응답이 나타나면 자동 감속이 아니라 즉시 중단하고 운영자에게 알린다.
- 동시에 여러 탭에서 상세 글을 열지 않는다.

초기 기본값은 Phase 0의 실제 응답 시간과 대상 글 수를 측정한 뒤 정한다. 근거 없는 고정 숫자는 계획 단계에서 확정하지 않는다.

### 최초 백필

1차 백필은 `menuId=0` 전체글 단일 피드 하나만 순회한다. "게시판별 순회"와 "일부 게시판만 실패" 같은 상태는 단일 피드에서는 존재하지 않는다 — 실패는 run 단위(succeeded/partial/failed/interrupted)로만 표현한다.

1. 대상 범위(시작일 또는 최대 페이지)를 계산하고 실행 전 예상 페이지 수를 표시한다.
2. 이진 탐색으로 범위 시작 위치를 찾는다(0절 절차).
3. 확장에 한 페이지를 요청하고, 페이지 단위로 파싱·검증한 뒤 DB에 업서트하며 anchor 커서를 확정한다(4.4절).
4. 빈 페이지, 범위보다 오래된 글, 반복 페이지, 최대 안전 페이지 중 하나에서 멈춘다.
5. 게시판 정보는 목록 행의 `board_id`·이름을 `cafe_boards`에 upsert하는 방식으로만 축적한다.
6. 목록에 없는 필드의 상세 탐색은 별도 큐에 넣고 속도 상한 안에서 순차 처리한다(후속 단계).

전체 이력의 양과 서버 부하를 알기 전에는 무제한 백필을 기본값으로 두지 않는다.

### 정기 증분 수집

- 첫 페이지부터 읽어 이미 저장된 연속 구간과 만날 때까지 진행한다.
- 글 ID만으로 정렬을 추정하지 않고 `posted_at`과 기존 ID 집합을 함께 사용한다.
- 공지 글은 매 페이지 반복될 수 있으므로 ID로 중복 제거한다.
- 새 글 저장과 함께 최근 글의 지표를 재관측한다.
- 삭제 여부는 “최근 범위를 여러 번 완전 탐색했는데 없음” 또는 상세 조회의 명시적 삭제 응답으로만 판정한다.

### 지표 재관측 정책

모든 과거 글을 매 실행 다시 읽으면 비용이 선형 증가한다. 비교 가능한 지표를 위해 글 나이를 기준으로 재관측한다.

- 0~24시간: 각 정기 수집 때
- 2~7일: 하루 1회
- 8~30일: 주 1회
- 30일 초과: 월 1회 또는 수집 종료

실제 목록 API가 임의의 과거 글을 저렴하게 갱신할 수 있는지 선행 조사 후 조정한다. 정확한 1시간 지표가 필요하다면 스케줄 주기와 관측 버킷을 별도로 정의한다.

## 6. 프로토콜과 모듈 경계

기존 자동화 메시지는 유지하고 다음과 같은 읽기 전용 메시지를 별도로 추가한다.

- `COLLECT_BOARD_PAGE` / `BOARD_PAGE_COLLECTED`
- `POST_COLLECTION_PROGRESS`
- 수집 run ID를 지정하는 `ABORT` 확장(4.4절 종료 상태 기계와 연결)
- 후속: `DISCOVER_BOARDS` / `BOARDS_DISCOVERED` — 1차는 단일 피드만 사용하고 게시판 정보를 목록 행에서 얻으므로, 게시판별 순회가 실제로 필요해질 때 추가한다
- 후속: `NAVIGATE_POST_DETAIL` / `POST_DETAIL_COLLECTED`
- 후속: `POST_DETAIL_PROGRESS`

한 페이지 응답(50건)의 byte 상한을 계약에 명시하고 데스크톱 WebSocket 서버의 `maxPayload`를 그에 맞춰 제한해, 비정상 응답이 메모리를 키우지 못하게 한다.

2026-08-30 Phase 3 첫 구현은 parsed `BOARD_PAGE_COLLECTED` payload의 보수적 상한을 256KiB로 둔다. raw JSON은 WebSocket으로 보내지 않으며, extension `BoardPageReader`는 정확히 `menuId=0`의 50건 한 페이지를 fetch·parse한 뒤 응답한다. HTTP/JSON/parser 실패는 body를 포함하지 않는 안정 오류 코드로만 반환한다. `createNaverReadGate(createCollectGate(bridge))`가 기존 같은 범위 `COLLECT` 합류를 유지하면서 대기 `COLLECT`를 다음 board page보다 먼저 실행한다.

새 도메인 타입은 `RawCandidate`를 재사용하지 않고 1차에 `CollectedPostMetadata`를 둔다. 후속 상세 단계에서만 `CollectedPostDetail`을 추가한다. 파서는 네트워크나 DB를 모르고, 확장 클라이언트는 저장 정책을 모르며, 데스크톱 수집 서비스만 커서와 트랜잭션을 관리한다.

확장에는 역할이 다른 두 실행기를 둔다.

- `BoardPageReader`: 세션 기반 단일 페이지 요청과 응답 내 다음 커서 해석 담당
- 후속 `PostDetailNavigator`: 전용 탭 생성, DOM 클릭, 로딩 대기, 상세 DOM 읽기 담당

후속 `PostDetailNavigator`는 CSS 선택자를 여러 계층에 흩어 두지 않고 페이지 계약 모듈 한곳에 모은다. 선택자 실패를 빈 값으로 성공 처리하지 않고 `PAGE_SHAPE_CHANGED`로 보고한다.

`BoardPageReader`는 다음 페이지를 스스로 요청하지 않는다. 장기 페이지 루프는 데스크톱이 한 페이지씩 지시하므로 MV3 서비스 워커가 중간에 종료되어도 마지막 커밋 페이지부터 재개할 수 있다.

기존 가입인사 `COLLECT`와 새 `COLLECT_BOARD_PAGE`는 공용 Naver read gate에서 직렬화한다. 이 게이트는 기존 `createCollectGate`를 수정해 만들지 않는다 — `createCollectGate`는 동일 `sincePostedAt` 요청을 한 walk에 합치는 고유 의미가 있으므로 그대로 두고, 그 바깥을 감싸는 새 계층(`createNaverReadGate(createCollectGate(bridge))` 형태)이 `COLLECT` walk와 단일 `COLLECT_BOARD_PAGE` 요청을 페이지 경계에서 직렬화한다. 우선순위는 가입인사 실행/미리보기, 전체글 백필, 세션 워밍 순서다. 백필은 한 페이지 저장을 원자 단위로 삼아 가입인사 요청이 들어오면 현재 페이지 커밋까지만 끝내고 다음 페이지를 요청하지 않은 채 양보한다. 가입인사 수집과 실행이 끝나면 마지막 커밋 anchor 기준으로 백필을 재개한다(양보 시간이 길었다면 4.4절의 재위치 절차를 따른다). 실행 중인 HTTP 요청을 강제로 끊어 부분 응답을 저장하지 않는다.

프로토콜 버전을 올리고 구버전 확장이 연결되면 명시적으로 업데이트 필요 상태를 보여준다. 사용자 노출 문구는 모두 `src/shared/text.ts`에 둔다.

이 기능은 쓰기 자동화 카탈로그에 두 번째 자동화로 등록하지 않는다. `AUTOMATIONS`와 `assertRuntimesRegistered`는 기존 가입인사 실행 기능에만 유지하고, 전체 게시판 수집은 별도 collection route, renderer API, IPC namespace로 노출한다. 이로써 승인·템플릿·실행 상태 의미가 수집 기능에 섞이지 않게 한다.

## 7. Drizzle/PostgreSQL 구현 원칙

Context7에서 확인한 현재 Drizzle 공식 문서 기준으로 다음 패턴을 사용한다.

- 복합 키 충돌 대상은 `onConflictDoUpdate({ target: [col1, col2], ... })`로 명시한다.
- 여러 행은 `.values(rows)`로 묶고 `excluded.<column>`을 사용해 최신 메타데이터를 업서트한다.
- 게시글 업서트, 관측값 삽입, 실행 카운트 갱신, 커서 확정을 한 트랜잭션에 묶는다.
- 수집 스키마는 `pgTable`로 선언하고 기존 SQLite 스키마와 파일을 분리한다.
- PostgreSQL 전용 Drizzle config와 migration 폴더를 두고 `drizzle-kit generate`로 생성한다.
- 앱 부팅 시 PostgreSQL 마이그레이션을 무조건 자동 실행하지 않는다. 배포 절차에서 먼저 적용하고 앱은 요구 스키마 버전을 확인한다.
- 시각은 `timestamptz`, KST 날짜 경계는 `src/shared/kst.ts`로 계산한 절대 시각을 사용한다. 3일·월 단위 범위가 필요하므로 `kstDayRange`에 더해 다일/월 범위 helper를 `kst.ts`에 추가하고 KST 자정 fixture로 검증한다. PostgreSQL session timezone은 표시 편의일 뿐 경계 계산의 원천이 아니다.
- 조회·댓글·좋아요 카운터는 장기 증가와 외부 값 범위를 고려해 `bigint`를 사용하고 애플리케이션 변환 경계를 테스트한다.
- 운영 반복 수집은 50건 multi-row `INSERT ... ON CONFLICT`; 초기 이관·복구 도구만 PostgreSQL `COPY`를 사용한다.
- 커넥션 풀은 Electron 앱 한 인스턴스에 맞게 작게 제한하고 앱 종료 시 명시적으로 닫는다.

동일 카페·피드의 수집 실행은 애플리케이션 게이트와 DB 수준 잠금으로 이중 방지한다. 여러 앱 인스턴스가 실수로 연결돼도 하나만 `menuId=0` 커서를 전진시킬 수 있어야 한다. 잠금은 세션 수준 advisory lock을 장기 휴지 내내 붙잡는 방식이 아니라, 페이지 트랜잭션 안에서 커서 행 `SELECT ... FOR UPDATE`(또는 transaction-level advisory lock)를 획득하는 방식을 사용한다 — 커서 확정이 원자적이면 기본 `READ COMMITTED`로 충분하고, 트랜잭션 밖 시간에는 어떤 잠금도 유지하지 않는다.

## 8. 구현 단계

### Phase 0 — 응답 조사와 fixture

- 일반 게시판/메뉴 API 요청을 캡처하고 필드 계약 문서화
- 정상·공지·말머리·비밀·삭제·권한 실패 fixture 익명화
- `menuId=0`, `viewType=L`, `size=50`, `page=N` 전체글 단일 피드 요청 계약 확정
- 글 ID의 카페 단위 유일성 검증
- 전체글보기 페이지 버튼이 호출하는 목록 요청과 응답 캡처
- 페이지 크기, 임의 페이지 접근, 전체 글 수, 공지 숨김 요청 파라미터 확정
- 목표 필드별 `목록 수집 가능`, `null`, `후속 상세 필요` 출처 표 작성
- `page_identity` 계산 규칙 확정: 정렬된 일반 글 ID 목록 기반 해시, 공지 제외·빈 페이지 처리 규칙과 fixture 기대값 포함
- 요청한 큰 page가 page 1로 조용히 돌아오는 silent fallback을 page 1 identity와 timestamp 범위로 탐지
- 과거 글 작성 timestamp의 정밀도(millisecond/minute/day) 확정 — 이진 탐색과 경계 처리(0절)의 전제 조건
- 실제 목록 API의 host 확인과 manifest `host_permissions` 대조 — 현재 허용 목록(`cafe.naver.com`, `apis.naver.com`)에 없으면 manifest와 관련 테스트를 함께 갱신
- 오류 분류표 작성: 429/403/연속 5xx/timeout/DNS/socket reset/malformed JSON/HTTP 200 로그인 HTML 각각의 재시도 가능 여부와 run 종결 상태(partial/failed) 판정

완료 기준: 추측 필드 없이 fixture에서 모든 1차 목록 필드와 다음 페이지 토큰을 파싱할 수 있고, 상세 없이는 얻지 못하는 필드가 명확히 후속 범위로 분리되며, `page_identity`·timestamp 정밀도·API host·오류 분류표가 문서로 확정된다.

### Phase 1 — 순수 타입과 파서

- 게시판/글/페이지 결과 타입 추가
- 숫자 서식(쉼표, 축약 표기), null, KST 시각 파서 추가
- 중복·반복 페이지·응답 envelope 검증

### Phase 2 — DB 스키마와 저장소

- `pg`와 Drizzle `node-postgres` 드라이버 도입
- PostgreSQL 연결 설정, 최소 권한 수집 계정, TLS·timeout·pool 구성
- 별도 Drizzle PostgreSQL schema/config/migration 폴더 추가
- `cafe_boards`, `cafe_posts`, `post_metric_observations`, `collection_runs`, `collection_feed_state`와 인덱스 추가
- 게시글 bulk upsert, 관측 삽입, run/state 저장소 추가
- 트랜잭션 롤백, 연결 단절, 동일 페이지 재시도, 중복 수집, null과 0 구분 테스트

완료 기준: 같은 페이지를 두 번 저장해도 글 수는 같고 관측 정책에 따른 이력만 추가된다.

2026-08-30 구현 메모: `drizzle-collection/`에 PostgreSQL 전용 migration과 `drizzle.collection.config.ts`를 분리했고, `DATABASE_URL`은 desktop collection DB 모듈에서만 받는다. `run_kind`는 날짜에 고정된 smoke 이름 대신 범용 `development`/`backfill`/`incremental`을 쓴다. 페이지 저장은 boards/posts upsert, list 관측 `DO NOTHING`, run counter 갱신, `state_version`+`anchor_post_id IS NOT DISTINCT FROM` CAS를 하나의 transaction으로 묶는다. 이 작업 시점의 로컬 `127.0.0.1:5432`는 응답하지 않아 기존 클러스터를 시작·변경하지 않았고, `COLLECTION_TEST_DATABASE_URL`로 명시한 별도 test DB가 준비되면 실제 migration/rollback 통합 테스트를 추가 실행한다.

`pnpm db:collection:generate`는 DB에 연결하지 않으며 Drizzle Kit config type이 요구하는 URL 자리에 inert placeholder를 쓴다. 실제 적용은 반드시 `COLLECTION_MIGRATION_DATABASE_URL`을 요구하는 `pnpm db:collection:migrate`만 수행한다. `pnpm test:collection:integration`은 `COLLECTION_TEST_DATABASE_URL`가 있고 DB 이름이 `_test` 또는 `_testing`으로 끝나는 **빈 전용 DB**에서만 migration을 적용한다. 통합 테스트는 종료 시 collection tables, enum types, migration journal을 제거하며, URL이 없으면 Vitest에서는 명시적으로 skip한다.

### Phase 3 — 확장 프로토콜과 게시판 수집기

- 새 메시지와 프로토콜 버전 추가
- Chrome 세션 기반 단일 페이지 읽기 클라이언트 구현
- 데스크톱 주도의 페이지 커서 전진, 진행 보고, 반복 페이지/안전 상한, 취소 처리
- 기존 가입인사 `COLLECT`와 별도 코드 경계 유지
- 기존 `createCollectGate`는 수정하지 않고 그 바깥에 `COLLECT`와 `COLLECT_BOARD_PAGE`를 함께 직렬화하는 공용 Naver read gate 계층 추가
- manifest에 `minimum_chrome_version: "116"` 추가 확정 — WebSocket 트래픽이 MV3 서비스 워커 idle timer를 갱신하는 동작이 Chrome 116부터이므로 현재 keep-alive 전제의 명문화다
- 한 페이지 fetch 핸들러는 30초 이내로 제한(MV3 워커 종료 한계); 20페이지·100페이지 장기 휴지 동안 PING만으로 워커가 유지되는지 실측 검증

완료 기준: 한 페이지 커밋 직전/직후에 서비스 워커와 앱을 각각 종료해도 마지막 커밋 anchor 기준으로 재개한다. mock HTTP로 목록 페이지 실패와 재시작을 재현한다. 백필 도중 가입인사 `COLLECT`가 들어오면 다음 페이지 전에 양보하고 가입인사 종료 뒤 정확한 페이지에서 재개한다. 상세 글 URL로 이동하거나 본문을 요청하지 않았음을 테스트로 확인한다.

### Phase 4 — 데스크톱 오케스트레이션

- 단일 전체글 피드 작업 계획, 날짜 페이지 이진 탐색, anchor 커서 확정·rewind 연속성 검증(4.4절) 구현
- 최초 백필과 정기 증분 모드 분리
- 최근 글 재관측 스케줄 구현
- 종료·취소 상태 기계(4.4절) 구현; 앱 시작 시 `running`으로 남은 run을 interrupted로 정리

완료 기준: 페이지 저장 전 종료 시 같은 페이지를 다시 읽고, 커서 확정 뒤 종료 시 다음 위치부터 읽는다. 장기 중단 후 재개 시 저장된 페이지 번호가 아니라 anchor 글 ID로 재위치함을 페이지가 이동한 mock 피드로 검증한다. rewind 검증이 간극을 감지하면 재탐색으로 전환함을 테스트한다.

### Phase 5 — 운영 UI

- 전체 수집 활성화, 제외 게시판(단일 피드에서 해당 게시판 행의 저장 제외), 백필 시작일/최대 페이지 설정
- 마지막 실행 시각(KST), 전체글 피드 성공/실패, 진행량, 다음 실행 표시
- 수동 “지금 수집”과 중단·실패 run의 이어서 재개 제공
- 목록 수집 처리량, 현재 페이지, 저장 글 수 표시
- PostgreSQL 연결 상태, 테이블·인덱스 크기와 관측 보존 정책 표시

UI는 자동화 카탈로그의 두 번째 항목이 아니라 독립적인 “게시글 데이터 수집” route로 추가한다. 승인·템플릿 메뉴는 제공하지 않으며, 1차에는 수집 설정·실행 상태·게시판 상태만 표시한다.

완료 기준: 운영자가 “수집할 글이 없음”과 “수집 실패”를 구분할 수 있다.

### Phase 6 — 검증과 첫 지표

- 파서·저장소·프로토콜·재시작 통합 테스트
- `typecheck`, 전체 Vitest, lint, build 실행
- 실제 계정으로 매우 작은 범위의 수동 검증
- 원본 테이블만으로 일별 글 수와 목록 관측 시점의 조회·댓글 분포 쿼리를 작성해 분석 가능성 검증

완료 기준: 샘플 DB에서 목표 질문 중 최소 두 가지를 재수집 없이 답한다.

### 후속 Phase — 상세 본문과 좋아요 수 (Phase 6 이후, 별도 계획)

1차 목록 수집이 운영에서 안정화된 뒤 별도 구현 계획으로 착수한다.

- `post_detail_tasks` 마이그레이션과 상세 작업 상태 저장소
- `CollectedPostDetail` 및 상세 프로토콜
- `PostDetailNavigator`의 실제 클릭·로딩·복귀 상태 기계
- 본문 저장 모델, 수정 이력, 개인정보 보존 정책
- 좋아요 수와 정확한 상세 작성 시각 관측
- 전용 탭 discard/freeze/remove 복구와 상세 탐색 상한

## 9. 테스트해야 할 실패 시나리오

- 로그인 만료 또는 권한 없는 게시판
- HTTP 200이지만 로그인/오류 HTML인 응답
- 페이지 1과 2 사이에 새 글이 생겨 항목이 밀림 — rewind 연속성 검증이 간극을 감지하는지
- 장기 중단 후 재개 시 anchor 글이 삭제·이동된 경우의 fallback 재위치
- 공지 글이 모든 페이지에 반복됨
- 제목/말머리/닉네임 변경, null 필드, 매우 큰 카운터
- 중간 페이지 실패, WebSocket 단절, 앱 강제 종료
- 일부 페이지 실패로 partial로 종결된 실행과 그 재개
- 게시판 삭제/이름 변경/글 이동
- 같은 시각에 여러 글 및 같은 글의 반복 관측
- KST 자정 전후 게시글과 화면 표시

## 10. 운영·보안·보존 정책

- 쿠키/세션은 현재 원칙대로 Chrome 밖으로 반출하지 않는다.
- PostgreSQL 접속 정보는 확장이나 renderer로 전달하지 않고 Electron main process에서만 사용한다.
- 수집 DB 계정은 수집 schema의 필요한 DML 권한만 가지며 migration 권한과 분리한다.
- 본문·댓글·프로필 이미지 등 목표 밖의 개인정보는 저장하지 않는다.
- 작성자 ID는 분석에 필요하지만 내보내기 기능에서는 기본 비식별화한다.
- 요청 속도는 고정 간격이 아니라 제한 범위 내 지연을 사용하고, 429/차단 징후에는 즉시 중단한다.
- run 오류에는 응답 전체가 아니라 상태 코드와 짧고 정제된 진단만 저장한다.
- PostgreSQL 백업/내보내기에는 스키마 버전과 KST 기준 설명을 포함한다.

초기에는 관측값을 삭제하지 않는다. 실제 증가량과 DB 크기를 한 달 측정한 뒤 보존/압축 정책을 결정한다.

## 11. 구현 전 확정할 제품 결정

1. “전체 게시판”에 운영진/비밀/특수 게시판도 포함할지, 기본 제외할지
2. 최초 백필 범위: 전체 이력, 특정 시작일, 또는 최대 페이지
3. 정기 수집 주기와 정확히 비교하고 싶은 반응 시점(예: 게시 후 24시간/7일)
4. 작성자 ID 처리 방식 — raw 저장 / 저장 시점 가명화 / 내보내기 시점만 가명화 중 하나를 명시적으로 선택
5. 제목 변경 이력과 삭제 글 상태가 실제 분석 요구에 포함되는지
6. 목록에 없는 필드를 위해 실제 탐색할 최대 글 수와 허용 시간대

이 중 1번(수집 대상 범위)과 4번(작성자 ID 처리)은 스키마와 내보내기 설계에 직접 영향을 주므로 Phase 2 착수 조건이다 — 확정 전에는 마이그레이션을 작성하지 않는다.

2026-08-30 Phase 2 착수 결정: `menuId=0` 일반 `ARTICLE` 행은 모든 게시판 분류를 저장한다. `writerInfo.memberKey`는 PostgreSQL 내부 원본으로 저장하고, 향후 내보내기 경계에서만 가명화한다. 이 결정은 수집 범위를 숨은 게시판별 allowlist로 축소하지 않으며, raw member key를 renderer·확장·내보내기 기본값에 전달하지 않는다.

권장 기본값은 일반 게시판만 포함, 특수/권한 제한 게시판 제외, 최근 1년 백필, 1일·7일 반응 관측, 작성자 ID 내부 저장/외부 비식별화다. 상세 탐색은 목록에 없는 필드에만 사용하고 수집 전용 단일 탭에서 순차 실행한다. 구체적인 처리 상한은 API 및 페이지 비용을 확인한 뒤 확정한다.

## 12. 핵심 판단

이 기능은 기존 가입인사 자동화의 수집 범위를 넓히는 작은 변경이 아니라 독립적인 읽기 전용 데이터 수집 서브시스템으로 다룬다. Chrome 확장 → WebSocket → Electron 수집 경계는 유지하되 게시글·관측·수집 커서는 PostgreSQL을 단일 원본으로 사용한다. 기존 가입인사 자동화와 앱 설정은 현재 SQLite를 유지한다. PostgreSQL 저장 성공과 커서 전진을 한 트랜잭션으로 묶고, 커서의 신뢰 원천을 페이지 번호가 아니라 anchor 글 ID에 두며, 연결 실패 시 안전하게 멈춘 뒤 같은 위치에서 멱등 재개하는 것이 핵심이다.
