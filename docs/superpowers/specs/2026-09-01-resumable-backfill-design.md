# 나누어 이어 하는 백필 설계

- 작성일: 2026-09-01 (KST)
- 대상: 카페 전체글 피드 수집(계획서 `2026-08-29-cafe-wide-post-collection.md`)의 이어받기 로직
- 상태: 설계 확정, 구현 전

## 1. 이 기능이 무엇인가

**정해진 과거 기간의 글을 서버에 부담을 주지 않는 속도로 천천히 DB에 옮겨 두는 것**이다. 실시간 모니터링이 아니고, 지금 이 순간의 조회 수·댓글 수가 목적도 아니다. 카운터는 글을 옮길 때 따라오는 부수적인 값이며 그 시점의 스냅샷으로 한 번 적히면 그만이다.

여기서 따라 나오는 것들:

- 기간이 먼저 정해지고 작업은 그 기간을 향해 진행한다. "최근 N일"처럼 실행할 때마다 움직이는 창이 아니다.
- 한 번에 끝나지 않는 것이 정상이다. 3일치가 26쪽·13분이었으므로 1년치는 약 3,200쪽이고, 페이지마다 5~9초를 쉬므로 하루에 끝나지 않는다.
- 속도를 올리는 최적화는 하지 않는다. 요청 간격과 휴지는 병목이 아니라 설계다.
- 재관측은 목적이 아니다. 같은 글을 다시 읽는 일은 이어붙이기에서 겹치는 페이지 때문에 생길 뿐이다.

## 2. 지금 구현이 이 목적과 어긋나는 곳

코드를 읽어 확인한 네 가지다.

| # | 어긋난 곳 | 근거 |
|---|---|---|
| 1 | 실행마다 커서를 초기화한다 | `collectionRunner.ts`가 `resumeFromCheckpoint: false`를 고정으로 넘긴다. 예약 실행이 반복돼도 작업이 앞으로 나아가지 못한다. |
| 2 | 대상 기간이 실행할 때마다 움직인다 | `collectionLoop.ts`가 `scheduledCollectionRange(now)`로 "지금부터 N일 전"을 매번 새로 만든다. 기간이 매번 달라 이어받기 자체가 거부된다. |
| 3 | 예산 소진이 실패로 남는다 | `MAX_PAGE_LIMIT`이 예외로 던져져 run이 `failed`가 된다. "정상적으로 여기까지"와 "무언가 잘못됨"이 구분되지 않는다. |
| 4 | 이어받기가 페이지 번호 근처만 훑는다 | `locateAnchor`가 저장된 번호 ±24쪽을 순차로 읽는다. 6시간 뒤(약 3.5쪽 이동)에는 맞지만 며칠 뒤에는 놓치고, 놓치면 기간의 처음부터 다시 시작한다. |

## 3. 작업과 실행을 나눈다

- **작업(job)**: 고정된 대상 기간과 커서를 가진 하나의 목표. `feed_state`가 이것을 들고 있다 — `target_start_ms`/`target_end_ms`가 기간, `anchor_post_id`·`anchor_posted_at`·`reference_page`가 어디까지 옮겼는지다.
- **실행(run)**: 그 작업을 향한 한 번의 시도. `runs`의 한 행이며 자기 몫의 페이지 예산을 쓰고 끝난다.

작업 하나에 실행이 여럿 달린다. 실행이 끝났다고 작업이 끝난 것이 아니다.

작업은 **한 번에 하나만** 존재한다. 스키마의 feed당 running run 유일 제약이 이를 강제한다.

진행 중인 작업이 있는데 운영자가 다른 기간을 지정하면, 지금은 `ALREADY_RUNNING`으로 거절할 뿐이다. 대신 다음 순서를 따른다.

1. 요청한 기간이 진행 중인 작업의 기간과 같으면 그냥 이어받는다(교체가 아니다).
2. 다르면 진행률과 지금까지 옮긴 건수를 보여주고 교체할지 묻는다.
3. 확인을 받으면 진행 중인 실행을 페이지 경계에서 멈추고, 커서를 새 기간으로 초기화한 뒤 시작한다. 이미 옮긴 글은 지우지 않는다 — 다음에 같은 기간을 다시 걸면 그만큼 덜 읽는다.

### 대상 기간

운영자가 시작·끝 날짜를 직접 고른다(KST 자정 경계). 최대 31일 제한은 유지하지 않는다 — 이 기능의 목적이 긴 기간을 나누어 옮기는 것이므로, 길이는 제한 사유가 아니다.

제한을 없애는 대신 **시작 전에 규모와 소요를 말해 준다**(§7의 실측 처리량 기준). 3년치는 약 9,300쪽이고 하루 49일치 속도면 23일이 걸린다 — 이 숫자를 보고 시작하는 것과, 모르고 시작해 한 달 뒤 "멈춘 것 같다"고 여기는 것은 다르다.

## 4. 한 번의 실행이 끝나는 방식

| 끝난 이유 | run 상태 | `stop_reason` | 커서 | 작업 |
|---|---|---|---|---|
| 기간의 시작에 도달 | `succeeded` | `null` | 확정 | 완료 |
| 페이지 예산 소진 | `partial` | `PAGE_BUDGET_SPENT` | 유지 | 진행 중 |
| 운영자 중지·앱 종료 | `interrupted` | `ABORTED` | 유지 | 진행 중 |
| 목록 형식 오류·연결 끊김 | `failed` | 오류 코드 | 유지 | 진행 중 |

예산 소진은 실패가 아니다. 정상적인 중간 정지이며 다음 실행이 이어받는다.

작업 완료 여부는 별도 플래그가 아니라 커서로 판별한다 — `anchor_posted_at`이 `target_start_ms`보다 오래되면 그 기간은 끝난 것이다. 상태를 두 곳에 적으면 어긋난다.

## 5. 이어받기: 카페의 네비게이션을 그대로 쓴다

### 전제

역시간순 피드는 새 글이 위에 쌓이므로 **옛 글은 시간이 갈수록 더 큰 페이지 번호로 밀린다**. 실측 게시량은 주간(09~21시) 시간당 26.4건, 야간 13.4건이다. 공백별로 얼마나 밀리는지:

| 공백 | 밀림 |
|---|---|
| 블록 사이 휴식 2시간 | 53건 ≒ **1쪽** |
| 밤사이 (21→09시) | 161건 ≒ 3.2쪽 |
| 주말 이틀 | 850건 ≒ 17쪽 |
| 일주일 | 2,975건 ≒ 60쪽 |

**정상 운영에서 압도적으로 흔한 경우는 한 쪽 남짓이다.** 되찾기는 이 경우를 가장 싸게 처리해야 하고, 드문 긴 공백에서만 비싼 수단을 꺼내야 한다.

### 되찾기는 단계로 올린다

1. **저장된 페이지 그 자리를 읽는다.** anchor가 있으면 끝 — **요청 1회**. 밀림이 반 쪽 미만인 경우다.
2. **없으면 다음 페이지.** 있으면 끝 — **요청 2회**. 블록 사이 휴식(약 1쪽)이 여기서 끝난다. 하루 안의 모든 이어받기가 이 두 단계 안에 든다.
3. **그래도 없으면 묶음 점프로 올린다.** 밤사이·주말·앱이 꺼져 있던 경우다. 각 응답의 `lastNavigationPageNumber + 1`로 건너뛰다가 경계를 지나치면 그 사이에서 이진 탐색한다.

한 쪽씩 훑는 구간을 2쪽으로 끊는 이유는, 3쪽째부터는 이미 "하루 안"이 아니어서 점프가 더 싸기 때문이다. 밤사이 3.2쪽은 점프 한 번이면 지나치고 그 안에서 2~3회로 좁혀진다.

거꾸로(페이지 번호가 줄어드는 쪽)는 보지 않는다. 글이 삭제되면 옛 글이 앞으로 당겨질 수 있지만, 삭제는 새 글보다 훨씬 드물어 순 이동은 항상 뒤쪽이다. 1단계에서 읽은 페이지의 가장 오래된 글이 이미 anchor보다 오래됐다면 그때만 한 쪽 앞을 본다.

### 큰 이동의 단위는 응답이 알려준다

`pageInfo`에는 `lastNavigationPageNumber` 하나만 있다. 실측:

| 요청 페이지 | `lastNavigationPageNumber` | 묶음 |
|---|---|---|
| 1 | 10 | 1~10 |
| 300 | 300 | 291~300 |

묶음은 10쪽이고, 카페 UI의 "다음 묶음"은 `lastNavigationPageNumber + 1`이다. **이 값을 코드에 상수로 박지 않고 매 응답에서 읽어 다음 점프를 정한다.** 카페가 묶음 크기를 바꿔도 그대로 맞는다.

### 경계 판정

3단계로 올라갔을 때, 어느 쪽에 있는지는 커서의 `anchor_posted_at`과 페이지의 글 시각을 견주어 정한다.

- 페이지의 **가장 오래된 글이 anchor보다 새것** → 아직 경계 앞이다. 계속 점프한다.
- 페이지의 **가장 새로운 글이 anchor보다 오래됨** → 지나쳤다. 직전 점프 지점과 이 지점 사이에서 이진 탐색한다.
- **anchor 시각이 페이지의 시각 범위 안에 든다 → 이 페이지가 경계다.**

경계 페이지에서는 anchor 글이 있으면 그 다음 글부터, 삭제되어 없으면 `anchor_posted_at`보다 오래된 첫 글부터 이어간다. 겹치는 몇 건은 멱등 upsert가 흡수하므로 빠뜨리는 것보다 겹치는 쪽을 택한다.

### 왜 "이미 저장된 글인가"를 1차 판정으로 쓰지 않는가

처음에는 페이지의 글 ID를 DB에 조회해 "이미 수집한 구간인지"로 경계를 찾으려 했다. 카페에 추가 요청이 들지 않는다는 장점이 있지만, **저장 여부는 이 작업의 진행과 같은 뜻이 아니다.**

깨지는 경우: 이전 작업이 지금 커서보다 **더 오래된** 구간을 이미 수집해 둔 경우다. 그러면 경계 너머의 페이지도 "전부 이미 있는 글"로 보여 섞인 페이지가 끝내 나타나지 않고, 점프가 진짜 이어받을 지점을 지나쳐 그 사이의 미수집 글을 통째로 건너뛴다. 저장 구간이 연속이라는 보장이 없는 한 이 신호는 안전하지 않다.

작성 시각은 그런 가정을 하지 않는다. anchor 시각은 이 작업이 어디까지 걸었는지를 가리키는 값이고, 다른 작업이 무엇을 저장했든 영향받지 않는다. anchor 글이 삭제되어도 시각은 커서에 남아 있어 그대로 쓸 수 있다.

DB 조회는 **보조 확인**으로만 쓴다 — 경계로 판정한 페이지의 글 중 이미 저장된 것과 아닌 것이 섞여 있으면 판정이 맞은 것이고, 전부 새 글이면 커서가 실제보다 앞을 가리키고 있었다는 신호다(그때는 한 묶음 앞으로 물러나 다시 본다).

### 커서가 없을 때

첫 실행이거나 anchor 글이 삭제되어 어디에도 없으면 이 절차를 쓸 수 없다. 그때는 기존 방식대로 **대상 기간의 끝을 향한 이진 탐색**(`findCollectionStartPage`)으로 시작 지점을 찾는다. 경로는 "커서가 있으면 네비게이션 이어받기, 없으면 기간 끝 탐색" 둘로 갈린다.

두 가지 종료 조건을 함께 둔다. 저장된 페이지 번호가 피드 끝을 넘어 **조용한 fallback**(요청 페이지 > `lastNavigationPageNumber`)으로 오면 커서를 믿을 수 없으므로 기간 끝 탐색으로 떨어진다. 점프하다 페이지의 가장 오래된 글이 **대상 기간의 시작보다 오래되면** 더 갈 곳이 없으므로 작업 완료로 판정한다.

### 예상 요청 수

| 공백 | 밀림 | 요청 |
|---|---|---|
| 블록 사이 2시간 | 약 1쪽 | **1~2회** |
| 밤사이 | 약 3.2쪽 | 3~4회 |
| 주말 이틀 | 약 17쪽 | 5~6회 |
| 일주일 | 약 60쪽 | 9~10회 |

하루 세 블록의 정상 운영에서 되찾기에 드는 비용은 **하루 3~6요청**이다. 곧장 묶음 점프부터 하면 같은 상황에 12~15요청이 든다.

## 6. 중복은 이미 막혀 있다

이어받을 때 겹치는 페이지를 다시 읽는 것은 설계상 정상이다. 글은 `post_id` 기준 upsert이므로 몇 번을 다시 읽어도 행이 늘지 않는다.

실측 근거: 3일 구간 재수집에서 1,287건을 관측해 **신규 105건·갱신 1,182건·중복 0건**. 조회수가 줄어든 행도 0건이었다 — 재관측이 엉뚱한 글에 붙지 않았다는 뜻이다.

## 7. 언제, 얼마나 도는가

### 운영 리듬

주기("몇 시간마다 한 번")가 아니라 **활동 시간대 + 작업·휴식 길이**로 정한다. 주기만으로는 새벽 3시에도 돌고, 한 번에 얼마나 일하는지도 말할 수 없다.

- **활동 시간대**: 기본 09:00~21:00 (KST). 이 밖에서는 시작하지 않는다.
- **작업 길이**: 기본 2시간. 한 번의 실행이 쓰는 시간이다.
- **휴식 길이**: 기본 2시간. 실행이 끝난 뒤 다음 실행까지 비우는 시간이다.
- **페이지 예산**: 작업 길이에 맞춰 정한다. 예산이 먼저 소진되면 남은 시간은 쉬는 것과 같다.

다음 실행 시각은 "직전 실행이 끝난 시각 + 휴식"이며, 활동 시간대 밖이면 다음 활동 시작으로 미룬다.

### 실측 처리량

지연 규칙(첫 요청 0, 이후 5~9초, 20번째마다 2~5분, 100번째마다 10~20분)을 그대로 계산하면 52요청에 777초로, 실측 780초와 맞는다. 그 위에서:

| | 값 |
|---|---|
| 카페 하루 생산량 | 425건 (8-29 458 · 8-30 417 · 8-31 401) |
| 2시간 블록에 들어가는 요청 | 299회 |
| 가입인사 양보(평균 21분 세션, 블록당 약 11분) 후 | 279회 |
| 하루 3블록 요청 | 837회 |
| 커밋 페이지 (요청 2회당 1쪽, rewind 포함) | 419쪽 |
| 수집 글 | 20,925건 |
| **하루에 옮기는 과거** | **약 49일치** |

- 3년치(약 9,300쪽) → **23일**
- 카페 전체(739,737건 · 14,795쪽) → **36일**

### 예산은 작업 길이에서 나온다

현재 기본값 `maxPages=99`는 25분 만에 소진되어 2시간 블록의 5분의 1만 쓴다. 작업 길이를 채우려면 **블록당 280 안팎**이 맞다. 설정 화면은 예산을 직접 묻는 대신 **작업 길이를 묻고 예산을 계산**해 보여준다 — 운영자가 다루는 단위는 "몇 쪽"이 아니라 "몇 시간"이다.

### 작업이 없으면

진행 중인 작업이 없으면 활동 시간대가 와도 **아무것도 하지 않는다**. 카페에 요청을 보내지 않는다. 작업은 운영자가 기간을 정해 시작한다.

예약은 "움직이는 창을 새로 수집하는 장치"가 아니라 "진행 중인 작업을 이어받는 장치"다.

## 8. 화면에 드러나는 것

- **작업 진행률**: 대상 기간 중 어디까지 왔는지. 커서의 작성 시각이 기간 안에서 차지하는 위치로 계산한다(이미 `collectionCoveragePercent`가 하는 일).
- **남은 양과 예상 완료일**: 남은 기간 × 하루 425건 ÷ 50으로 남은 쪽수를, 하루 처리량(§7)으로 완료일을 낸다. "3년치 중 8개월 옮김 · 남은 17일" 같은 문장이 목표다.
- **이번 실행이 끝난 이유**: 예산 소진인지 완료인지 오류인지가 목록에 그대로 보인다.

## 8.5 가입인사 세션과의 관계

수집은 가입인사 세션이 도는 동안 페이지를 요청하지 않고 기다린다(`isSessionBusy`). 기다리는 지점은 **페이지 요청 직전**이므로, 한 페이지를 반쯤 읽다 멈추는 상태는 존재하지 않는다.

세션 때문에 멈춘 사이에 실행이 끝나면 그 페이지는 커밋되지 않았으므로, 다음 실행이 **그 페이지를 통째로 다시 읽는다**. 저장은 페이지 단위 트랜잭션이라 절반만 들어간 페이지가 남지 않고, 다시 읽어도 upsert가 흡수한다.

## 9. 무엇을 하지 않는가

- 속도를 올리지 않는다. 지연·휴지는 그대로 둔다.
- 여러 작업을 동시에 돌리지 않는다.
- 증감 이력을 남기지 않는다. 글 행의 카운터는 마지막으로 읽은 값이다.
- 작업이 없을 때 "혹시 새 글이 있나" 확인하지 않는다.

## 10. 검증 기준

1. 예약 실행을 두 번 거쳐도 커서가 뒤로 물러나지 않고 앞으로만 간다.
2. 예산 소진으로 끝난 실행이 `partial`/`PAGE_BUDGET_SPENT`로 기록되고, 다음 실행이 같은 지점에서 이어받는다.
3. 며칠 공백 뒤 이어받아도 기간의 처음부터 다시 시작하지 않는다(요청 수가 밀린 양에 비례해 완만히 는다).
4. 이어받기가 만든 중복 글이 0건이다.
5. 작업이 없을 때 예약 시각이 지나도 카페 요청이 0건이다.
6. 기간의 시작에 도달하면 `succeeded`로 끝나고, 이후 예약 실행은 아무것도 하지 않는다.
