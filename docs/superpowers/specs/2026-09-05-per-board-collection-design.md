# 게시판별로 걷는 백필 설계

- 작성일: 2026-09-05 (KST)
- 대상: 카페 글 수집(설계 `2026-09-01-resumable-backfill-design.md`)의 피드 단위
- 상태: 설계 확정, 구현 전

## 1. 왜 바꾸는가

전체글 목록(0번 메뉴)은 **1000쪽까지만** 준다. 2026-09-05 직접 확인:

| 요청 | 응답 |
|---|---|
| 999쪽 | `lastNavigationPageNumber: 1000`, `visibleNextButton: true` |
| 1000쪽 | `lastNavigationPageNumber: 1000`, `visibleNextButton: false`, 마지막 글 05-04 |
| 1001쪽 이후 | 1쪽 내용을 그대로 돌려준다 (`lastNavigationPageNumber: 10`) |

한 페이지 50건이므로 이 피드로 닿는 것은 최근 5만 건이다. 하루 300건씩 쌓이므로 이 경계는 매일 6쪽씩 앞으로 밀린다. 2026-01-01부터의 백필은 이 피드로는 원리적으로 불가능하다.

게시판별 목록은 **게시판마다 따로** 1000쪽을 준다. 가장 큰 게시판(국내구입기, 137)의 1000쪽이 2025-08-12에 닿는다. 나머지는 더 멀리 닿는다. 게시판 단위로 걸으면 2026년 전체가 닿는다.

### 이번에 실제로 일어난 일

1. 09-04 18:20 실행이 0번 메뉴 1000쪽까지 저장하고 1001쪽을 요청했다. 앱은 14:15 빌드(`388feda`)라 피드 끝을 실패로 보았다. `BOARD_PAGE_SILENT_FALLBACK`.
2. 09-05 09:00 재개가 1000쪽부터 앵커를 찾았다. 밤사이 앵커는 1006쪽쯤으로 밀렸고 1001쪽은 1쪽으로 떨어졌다. `locateResumePosition`이 `unusable`을 돌려주었다.
3. 오케스트레이터는 `unusable`이면 **기간의 첫 페이지를 새로 찾는다**. 345쪽(08-01)부터 다시 걸었다. 신규 0건, 갱신 498건.

두 번째와 세 번째는 게시판별로 바꿔도 그대로 남는 결함이다. 이 설계가 함께 고친다(§5).

## 2. 무엇이 바뀌지 않는가

- 작업(job)과 실행(run)의 구분, 페이지 예산, 예약 블록, 강제 수집.
- 커서·앵커·CAS·이어받기(`collectionResume.ts`)·연속성 검증. 피드가 무엇이든 그대로 쓴다.
- `posts` 테이블과 upsert. 글은 게시판이 아니라 카페의 것이고, 같은 글이 두 피드에서 오면 한 행이다.
- 기간 입력, 지금 수집, 예약 시작, 중지, 강제 수집 버튼.

## 3. 작업의 모양

### 범위(scope)

작업은 둘 중 하나의 범위를 갖는다.

| 범위 | 피드 | 언제 쓰나 |
|---|---|---|
| **전체글** | `all_articles`, 메뉴 0 | 최근 며칠처럼 짧은 기간. 한 피드 26쪽이 게시판 38개 400쪽보다 싸다. |
| **게시판별** | `board`, 메뉴 = 게시판 id, 게시판마다 한 피드 | 전체글 한계(현재 약 4개월) 너머의 기간. **기본값.** |

기간 입력 옆에 선택이 하나 생긴다. 앱이 대신 고르지 않는다. 전체글이 한계에 닿으면 실행이 `FEED_HORIZON`으로 멈추고 화면이 "전체글 목록은 여기까지만 줍니다. 게시판별로 다시 시작하세요"라고 말한다(§5).

### 게시판별 작업은 행이 여럿이다

작업 하나가 `feed_state` **게시판 수만큼의 행**이다. 모두 같은 `target_start_ms`/`target_end_ms`를 갖고, 게시판마다 자기 앵커·`completed_at`·`forced_at`을 따로 가진다.

- 대상 게시판: `boards`에서 `collect_enabled = true`인 것. 지금 38개.
- 순서: 작업을 만드는 시점의 **DB 게시판별 글 수 내림차순**, 같으면 `board_id` 오름차순. `feed_state.queue_order`(정수, 1부터)에 적어 두고 다시 계산하지 않는다. 순서가 도중에 바뀌면 "어디까지 했는지"를 말할 수 없다.
- 작업이 **존재**한다 = `board` 행이 하나라도 있다. **완료**다 = 모든 `board` 행이 완료다. **강제**다 = 어느 행이든 `forced_at`이 있다(강제는 작업 단위로 켜고 끄며 모든 행에 같이 쓴다).
- 기간 교체는 모든 `board` 행을 함께 초기화한다. 게시판 목록도 그때 다시 읽고 순서도 다시 매긴다.

`all_articles` 행과 `board` 행이 동시에 있을 수 있다. **작업은 하나뿐**이라는 규칙은 유지한다: 새 범위의 작업을 만들면 다른 범위의 행은 지운다. `runs`는 `feed_state`를 참조하지 않으므로 지워도 기록은 남는다.

### 스키마

```sql
ALTER TYPE collection_feed_kind ADD VALUE 'board';
ALTER TABLE feed_state ADD COLUMN queue_order integer;
ALTER TABLE feed_state ADD COLUMN horizon_reached_at timestamp(3) with time zone;
ALTER TABLE feed_state ADD CONSTRAINT feed_state_queue_order CHECK (queue_order IS NULL OR queue_order >= 1);
```

`queue_order`는 `board` 행에만 있다. `horizon_reached_at`은 §5.

`runs.feed_kind`도 같은 enum이라 `board` 실행은 게시판 id를 `menu_id`에 적는다. 한 피드에 running 실행 하나라는 유일 제약은 게시판마다 따로 걸리는데, 러너가 한 번에 한 게시판만 걸으므로 실제로는 하나다.

## 4. 한 블록이 게시판을 이어서 걷는다

블록마다 게시판 하나만 걸면 글이 5개인 게시판에도 블록 하나(기본 2시간 일하고 2시간 쉼)를 통째로 쓴다. 글 100건 미만인 게시판이 20개다. 그래서:

- 러너는 대기열 순서로 **미완료 게시판을 차례로** 돈다.
- 페이지 예산은 **블록 전체가 공유**한다. 게시판 하나가 끝나면 남은 예산으로 다음 게시판을 잇는다. 예산이 다하면 그 자리에서 `partial`로 멈추고, 다음 블록이 같은 게시판의 커서에서 잇는다.
- 게시판마다 `runs` 한 행. 기록 단위는 지금과 같다.
- 중지 요청은 페이지 경계에서 지금 게시판을 `interrupted`로 끝내고 다음 게시판으로 가지 않는다.
- 게시판 하나가 `failed`로 끝나면 다음 게시판으로 **간다**. 한 게시판의 형식 오류가 나머지 37개를 막을 이유가 없다. 실패는 그 행에 남고 다음 블록이 다시 시도한다.

러너의 `start`는 지금처럼 즉시 돌아오고, 이어 걷는 것은 러너 안의 순차 루프다. 오케스트레이터는 피드 하나를 받아 하나를 걷는다는 계약을 유지하고, 결과에 **쓴 요청 수**를 더해 러너가 남은 예산을 계산한다.

### 게시판별 걷기의 첫 위치

게시판 피드는 커서가 없으면 지금과 같이 `findCollectionStartPage`로 기간 끝을 향해 이분 탐색한다. 게시판마다 약 10회다. 기간을 `2026-01-01 ~ 2026-05-05`로 잡으면 각 게시판이 05-05에 바로 내려앉아 이미 있는 5~7월을 다시 읽지 않는다.

## 5. 두 결함을 막는다

### 재개 위치를 잃으면 처음으로 돌아가지 않는다

`locateResumePosition`이 `unusable`이면 실행을 `failed` · `RESUME_POSITION_LOST`로 끝낸다. 커서는 그대로 둔다. 기간 끝 탐색으로 떨어지는 경로는 **커서가 없을 때만** 남는다.

되돌아가는 것이 왜 틀린가: 이미 옮긴 구간을 다시 읽는 데 블록 여러 개를 쓰고, 화면은 "07-30까지 내려왔습니다"라고 말해 운영자가 진행을 잃은 것으로 읽는다. 실패로 남기면 사유가 실행 목록에 찍히고 운영자가 기간을 교체할지 정한다.

### 피드 한계는 완료가 아니다

걷는 도중 요청한 쪽이 1쪽으로 떨어지면(조용한 fallback) 지금은 `succeeded`로 끝내고 작업을 완료로 적는다(`0714a10`). 피드가 정말 끝난 경우와 카페가 더 주지 않는 경우를 가른다.

| 직전에 저장한 쪽 | 뜻 | run | `feed_state` |
|---|---|---|---|
| 1000쪽 미만 | 피드의 자연스러운 끝. 기간 시작보다 오래된 글이 없다. | `succeeded` | `completed_at` |
| 1000쪽 | 카페의 한계. 그 아래에 글이 더 있을 수 있다. | `partial` · `FEED_HORIZON` | `horizon_reached_at`, 커서 유지 |

`horizon_reached_at`이 있는 피드는 예약이 다시 걷지 않는다(완료와 같은 취급). 화면에는 "카페가 여기까지만 줍니다"로 완료와 구분해 보인다. 기간을 교체하면 지운다.

한계 판정은 `visibleNextButton === false`가 아니라 **직전에 저장한 쪽 번호**로 한다. `visibleNextButton`은 마지막 묶음의 모든 쪽에서 false인지 아직 재지 않았다.

## 6. 화면

수집 현황의 작업 카드가 범위를 보여 준다.

- 전체글: 지금과 같다.
- 게시판별: 요약 한 줄(완료 n / 전체 38, 지금 걷는 게시판, 남은 게시판) 아래에 게시판별 표. 순서, 이름, 상태(대기·진행·완료·한계·실패), 커서 시각, 이 작업에서 옮긴 건수.

기간 입력의 범위 선택은 라디오 둘이다. 기본은 게시판별. 문구는 `src/shared/text.ts`.

## 7. 프로토콜

`COLLECT_BOARD_PAGE.menuId`가 `'0'` 상수에서 **숫자 문자열**로 열린다. 확장의 `cafeArticleListUrl(page, menuId)`가 메뉴를 받는다. 검증은 `/^\d+$/`. `PROTOCOL_VERSION`이 오른다 — 앱과 확장을 함께 다시 패키징해야 하고, 그러지 않으면 짝짓기가 조용히 죽는다(메모리 `repackage-after-protocol-bump`).

`cafeArticleFixture.ts`의 캡처 CLI 제약("이 엔드포인트만")은 메뉴가 변수가 되어도 유지된다. 경로의 카페 id와 엔드포인트는 그대로 상수다.

## 8. 옮기는 절차

1. 앱을 새로 패키징하고 확장을 다시 불러온다.
2. 지금 돌고 있는 전체글 실행을 중지한다.
3. 앱을 끄고 마이그레이션을 적용한다. 앱은 마이그레이션을 적용하지 않고 적용됐는지만 확인한다:
   ```bash
   COLLECTION_MIGRATION_DATABASE_URL=postgresql://lp2k@127.0.0.1:5432/whisky_manager_collection pnpm db:collection:migrate
   ```
4. 새 패키지를 띄운다.
5. 기간 `2026-01-01 ~ 2026-05-05`, 범위 게시판별로 작업을 만든다. 교체 확인이 뜬다(전체글 작업이 진행 중이므로).
6. 예약을 켠다. 첫 블록이 국내구입기부터 시작한다.

규모: 05-04 이전 4개월, 하루 300건이면 약 37,000건 · 750쪽에 게시판마다 탐색 10회 · 38개 = 380회. 블록당 예산이 약 150쪽이면 8블록, 하루 3블록이면 사흘이다.

## 9. 테스트

- `collectionResume`: `unusable`이 실행을 `RESUME_POSITION_LOST`로 끝내고 커서를 건드리지 않는다.
- `collectionOrchestrator`: 1000쪽 저장 뒤 fallback → `partial` · `FEED_HORIZON` · `horizon_reached_at`. 999쪽 뒤 fallback → `succeeded`.
- `collectionRunner`: 게시판 셋을 예산 안에서 이어 걷고, 예산이 다하면 멈추며, 하나가 실패해도 다음으로 간다. 중지는 다음으로 가지 않는다.
- `repository`: 게시판별 작업 생성이 순서를 글 수로 매기고, 교체가 모든 행을 초기화하며, 다른 범위의 행을 지운다.
- `collectionJob`: 존재·완료·강제가 행 여럿에서 맞게 모인다.
- `protocol`·`boardPageReader`: 메뉴 id가 URL에 들어가고, 숫자가 아닌 값은 거절된다.
- `statusQuery`: 게시판별 요약과 표.
