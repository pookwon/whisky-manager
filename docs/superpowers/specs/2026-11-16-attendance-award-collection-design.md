# 개근 기록 수집 설계

- 작성일: 2026-11-16 (KST)
- 대상: Member of the Month 게시판(메뉴 207)의 `[댓글 개근]`·`[게시글 개근]`·`[방문 개근]` 글
- 상태: 설계 초안, 게시판과 글 읽기 응답 실측 완료(§3), 구현 전

## 1. 왜 필요한가

카페는 열흘쯤마다 세 종류의 개근 글을 올린다. 글 하나가 한 회차이고, 본문에 그 회차를 달성한 회원의 닉네임이 나열된다. 이 기록은 글 속에만 있어서 "누가 몇 회차를 이어서 달성했는가", "회차마다 몇 명이 달성했는가" 같은 것을 셀 수 없다.

운영자가 원하는 것은 특정 지표 하나가 아니다. **닉네임과 달성 기간을 빠짐없이 저장해 두고, 그 위에서 여러 지표를 뽑을 수 있게 하는 것**이다. 그래서 이번 작업은 원본을 쌓는 데까지다.

## 2. 목표와 범위

**목표**
- 2021년 3월의 첫 개근 글부터 지금까지, 세 종류 모두의 닉네임과 기간을 수집 DB에 저장한다.
- 앞으로 올라오는 글도 같은 기능으로 계속 넣는다.
- 빠진 회차와 잘못 읽은 글이 있으면 운영자가 화면에서 알 수 있다.

**이번에 하지 않는 것**
- 연속 달성·누계 같은 통계 화면과 통계 조회. 저장된 원본에서 나중에 만든다.
- 닉네임을 회원 키(`members.member_key`)로 연결하는 일.
- 자동 실행(일정·월초 감지). 운영자가 버튼으로 실행한다.
- 같은 게시판의 다른 글(`[방문 히트]`, `[이주의 인기멤버]`, `[월간MoM]`, `[월간 탑 100]`, `[기여도 랭킹]` 등).
- CSV 내보내기.

**이렇게 되면 실패다**
- 잘못 자른 닉네임이 조용히 쌓인다.
- 회차가 빠졌는데 화면이 "다 됐다"고 말한다.
- 기존 수집 간격보다 빠르게 네이버에 요청한다.

## 3. 실측한 것 (2026-11-16)

로그인된 브라우저에서 게시판 목록과 글 읽기 응답을 직접 읽었다.

**게시판**
- 메뉴 207. 목록은 기존 목록 API(`cafe-boardlist-api/v1/cafes/14538121/menus/207/articles`)가 그대로 답한다.
- 50개씩 24쪽, 약 1,160글. 가장 오래된 개근 글은 148887번 `[방문 개근] 3월 1일~3월 11일`(2021-03-12 KST)이다. 개근 글은 약 600개다.

**제목**
- `[댓글 개근] 11월 1일~11월 10일 카페 댓글 개근상을 잡아라!` 꼴이다. 종류는 대괄호 안에, 기간은 `M월 D일~M월 D일`에 있다.
- 연도가 없다.
- 글은 기간 마지막 날 다음 날 07:02 KST쯤 올라온다.
- **기간은 달력에 맞춰져 있지 않다.** 2021년에는 11일짜리(`3월 1일~3월 11일`, `10월 16일~10월 26일`, `11월 3일~11월 13일`), 2023년에는 `2월 2일~2월 11일` 다음 `2월 12일~2월 21일`, 2026년에는 `10월 21일~10월 30일` 다음 `11월 1일~11월 10일`이다. 회차 사이에 하루가 비기도 한다.

**본문**
- 기존 글 읽기 응답(`article.cafe.naver.com/gw/v4/cafes/14538121/articles/{id}`)의 `result.article.contentHtml`에 본문이 있다. 지금 파서(`parseCafeArticle`)는 이 값을 읽지 않는다. 새 요청 주소는 필요 없다.
- 형식은 2021년부터 지금까지 같다. 소개 문장 뒤에 `닉네임님, 닉네임님, … 닉네임님이 당첨 되셨습니다. 축하드려요!`가 온다.
- 본문에는 닉네임만 있다. 회원 키나 링크는 없다.
- 닉네임에는 공백이 들어갈 수 있다. 한글·영문 모두에서 보인다.

## 4. 접근 방식

개근 글을 어떻게 찾느냐를 두고 세 가지를 견주었다.

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 게시판 목록 훑기** | 메뉴 207의 목록을 끝까지 읽어 제목으로 개근 글을 고른다 | 기존 게시글 수집 범위와 무관하게 2021년부터 빠짐없이 찾는다. 목록 읽기는 기존 것을 쓴다 | 실행할 때마다 목록 24쪽을 읽는다 |
| B. `posts` 테이블에서 찾기 | 이미 수집된 글 중 메뉴 207의 개근 글을 고른다 | 코드가 가장 적다 | 기존 수집이 닿지 않은 기간의 글이 조용히 빠진다 |
| C. 글 번호 직접 지정 | 운영자가 넣은 번호만 읽는다 | 만들기 가장 쉽다 | 과거 600개를 채울 수 없다 |

**운영자가 A를 골랐다.** 연속 달성을 세려면 빠진 회차가 없어야 하고, A만 그것을 스스로 보장한다.

수집 형태도 운영자가 정했다. 한 번 넣고 끝내는 작업이 아니라 **앱 기능**으로 만든다.

## 5. 구조

### 흐름

1. 운영자가 화면에서 수집을 시작한다.
2. 메뉴 207의 목록을 1쪽부터 글이 없는 쪽까지 읽는다(`COLLECT_BOARD_PAGE`, `menuId: '207'`).
3. 각 글의 제목을 제목 파서에 넣어 개근 글인지, 어느 종류·기간인지 판정한다.
4. 개근 글 중 아직 `recorded`로 저장되지 않은 글만 본문을 읽는다.
5. 본문 파서가 닉네임 목록을 뽑는다.
6. 글 하나의 결과(글 행과 닉네임 행 전부)를 한 트랜잭션으로 저장한다.
7. 끝나면 화면에 종류별 회차 수와 거부된 글을 보여 준다.

목록은 실행할 때마다 전부 읽는다. 24쪽이라 부담이 없고, "어디까지 읽었나"를 따로 기억할 필요가 없어진다. 건너뛰는 것은 본문 읽기뿐이다.

### 제목 파서 (`src/shared`, 순수 함수)

- 입력: 제목, 글 작성 시각(epoch ms). 출력: 종류와 기간, 또는 "개근 글 아님", 또는 "개근 글인데 기간을 못 읽음".
- 종류: `[댓글 개근]` → `comment`, `[게시글 개근]` → `post`, `[방문 개근]` → `visit`.
- 연도: 작성 시각의 KST 날짜를 D라 하면, 기간 종료일은 `M월 D일`이 D 이하가 되는 가장 늦은 해다. 시작일의 월·일이 종료일보다 뒤면(해를 넘긴 회차) 시작일은 그 전 해다.
- 종료일이 D보다 7일 넘게 앞서면 기간을 못 읽은 것으로 본다. 연도를 잘못 맞춘 채 저장하는 것을 막는다.
- 날짜 계산은 `src/shared/kst.ts`를 쓴다.

### 본문 파서 (`src/shared`, 순수 함수)

- 입력: `contentHtml`. 출력: 닉네임 배열(본문에 적힌 순서), 또는 거부 사유.
- 닉네임 목록은 `님이 당첨 되셨습니다`로 끝나는 덩어리다. `님, `로 나누고, 마지막 조각에서 `님이 당첨 되셨습니다` 이후를 뗀다.
- 쉼표로 나누지 않는다. 닉네임에 공백이 있고, `하느님`처럼 `님`으로 끝나는 닉네임은 `하느님님, `으로 적히므로 `님, `가 맞는 경계다.
- 거부하는 경우: 끝맺는 문구가 없다, 닉네임이 하나도 없다, 빈 닉네임이 나온다.
- 닉네임은 앞뒤 공백만 떼고 글에 적힌 그대로 둔다.
- 소개 문장과 닉네임 목록을 어떻게 가를지는 구현자가 정한다. §3의 실측 인원이 맞아야 한다.
- HTML 처리는 이미 의존성에 있는 `node-html-parser`를 쓴다.

### 본문 읽기 (확장 프로그램)

- 기존 `COLLECT_ARTICLE`은 그대로 둔다. id 탐색이 대량으로 쓰는 요청이라 본문을 실으면 모든 응답이 커진다.
- 본문을 싣는 새 요청·응답 한 쌍과 새 리더 파일을 추가한다. 주소·헤더·referer는 기존 글 읽기와 같다.
- 확장은 판단하지 않는다. `contentHtml`과 글 번호·제목·작성 시각을 돌려주고, 닉네임 파싱은 데스크톱에서 한다.
- 오류 응답에는 본문을 싣지 않는다. 기존 규칙과 같다(코드와 파서 규칙 이름만).
- 새 요청도 네이버 읽기 직렬화(`naverReadGate`)를 거친다.
- 요청 간격은 기존 수집 페이싱 설정을 따른다.

### 저장 (PostgreSQL 수집 DB)

새 스키마 파일 하나에 두 테이블을 둔다. 연속 횟수나 누계는 저장하지 않는다.

**`attendance_posts`** — 개근 글 하나가 한 줄, 곧 한 회차다.

| 열 | 내용 |
|---|---|
| `post_id` | 글 번호, 기본 키 |
| `kind` | `comment` / `post` / `visit` |
| `period_start`, `period_end` | KST 날짜. 기간을 못 읽은 글은 null |
| `title` | 글 제목 |
| `posted_at` | 글 작성 시각 |
| `status` | `recorded` / `refused` |
| `refusal_rule` | 거부 사유(파서 규칙 이름). `recorded`면 null |
| `winner_count` | 저장한 닉네임 수. `refused`면 null |
| `read_at` | 마지막으로 읽은 시각 |

**`attendance_awards`** — 한 번의 달성이 한 줄이다.

| 열 | 내용 |
|---|---|
| `post_id` | `attendance_posts` 참조 |
| `position` | 본문에 적힌 순서(1부터) |
| `nickname` | 글에 적힌 그대로 |

기본 키는 `(post_id, position)`, `nickname`에 인덱스를 둔다. 종류와 기간은 `attendance_posts`와 조인해 얻는다.

- `refused` 글은 닉네임을 한 줄도 저장하지 않는다. 다음 실행에서 다시 읽는다.
- `recorded` 글은 다시 읽지 않는다.
- 같은 종류·기간의 글이 둘 있어도 막지 않는다. 둘 다 저장하고, 통계를 낼 때 다룬다.
- 방문 개근은 한 글에 8천 줄 가까이 되므로 나눠서 넣되 한 트랜잭션 안에서 한다. 전체는 100만 줄을 넘을 수 있다.
- 마이그레이션은 `pnpm db:collection:generate`로 만들고 `pnpm db:collection:migrate`로 적용한다. 앱은 실행 중에 수집 DB를 마이그레이션하지 않는다.
- 쓰기 저장소와 읽기 조회를 따로 둔다. 기존 `memberRepository.ts`와 `memberStatusQuery.ts`의 구분을 따른다.

## 6. 나중에 통계를 낼 때 알아야 할 것

이번 범위는 아니지만 저장 형태가 이것을 막지 않아야 한다.

- **연속은 달력이 아니라 회차 순서로 센다.** 기간이 달력에 맞지 않고 사이에 하루가 비기도 하므로, 같은 종류의 글을 `period_start` 순으로 늘어놓은 것이 회차 순서다.
- **닉네임은 회원이 아니다.** 닉네임을 바꾼 회원은 다른 사람으로 보이고, 버려진 닉네임을 다른 회원이 쓰면 한 사람으로 합쳐진다. 회원 키로 잇는 근거는 `members.nickname`(현재)과 `posts.author_nickname`(글 수집 당시)뿐이고, 글을 쓴 적 없는 회원의 옛 닉네임은 이을 수 없다.
- 닉네임 자체에 `님, `가 들어 있으면 둘로 잘린다. 구분할 방법이 없어 받아들인다.

## 7. 테스트

- 제목 파서: §3의 제목들, 해를 넘기는 회차(`12월 22일~1월 1일`, 1월 2일 작성), 12월 30일에 끝나 12월 31일에 올라온 글, 개근 글이 아닌 제목, 기간이 깨진 제목.
- 본문 파서: 실제 응답 구조를 본뜬 픽스처로 인원과 첫·마지막 닉네임을 확인한다. 공백이 든 닉네임, `님`으로 끝나는 닉네임, 끝맺는 문구가 없는 본문.
- 픽스처의 닉네임은 지어낸 것으로 바꾼다. 기존 정리 함수(`sanitizeCafeArticleFixture`)가 `contentHtml`을 다루는지는 구현 때 확인한다.
- 저장소: 기존 수집 DB 통합 테스트 방식(실제 PostgreSQL)을 따른다. 거부된 글이 닉네임을 남기지 않는 것, 다시 실행해도 줄이 늘지 않는 것.
- 확장 리더: 기존 `articleReader` 테스트와 같은 꼴.

## 8. 구현자에게 맡기는 것

- 새 요청·응답의 이름과 프로토콜 버전을 올릴지 여부.
- 파일·모듈 이름. 도메인 말은 `attendance`(개근), `award`(달성)를 쓴다.
- 본문에서 소개 문장과 닉네임 목록을 가르는 방법.
- 수집 중 멈춤·취소 버튼을 둘지. 글 단위로 저장하므로 멈췄다 다시 실행하면 이어진다.
- 기존 수집 루프와 동시에 돌 때의 잠금. 기존 관례를 따른다.
