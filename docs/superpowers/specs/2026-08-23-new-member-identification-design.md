# 신입회원 판별 설계

> **이 설계는 폐기되었다.** [안내 댓글 없는 오늘 글 설계](2026-08-23-uncommented-greetings-design.md)가 대체한다. 여기 적힌 가입자 표·조회·보류는 더 이상 코드에 없다.
>
> 실제로 굴려보니 판정 근거가 카페 밖(회원 목록)에 있어 조회 실패마다 글을 보류해야 했고, 운영자가 실제로 보는 것은 "가입한 지 며칠인가"가 아니라 "이 글에 안내가 나갔나"였다. 왜 이렇게 만들었다가 왜 되돌렸는지가 남아야 하므로 문서는 지우지 않는다.

> 2026-08-23. [네이버 카페 자동화 설계](2026-08-22-naver-cafe-automation-design.md) §5.8(가입인사 모듈 명세)의 판단 하나를 뒤집는다. 나머지 절은 그대로 전제한다.

## 1. 목표

가입인사 자동 댓글이 **신입에게만, 한 번만** 나가게 한다. 두 가지를 고친다.

- **중복 환영** — 한 회원이 자동 생성 글과 직접 쓴 인사글을 둘 다 가지면 지금은 댓글이 두 번 나간다
- **대상 아닌 사람** — 오래 전에 가입한 회원이 가입인사 게시판에 쓴 글에도 지금은 댓글이 나간다

## 2. §5.8의 어떤 판단을 뒤집는가

§5.8은 이렇게 적었다.

> **가입인사는 두 종류가 섞여 들어온다.** ① 네이버가 가입 시점에 자동 생성하는 글 ② 회원이 직접 쓴 인사글. **둘 다 대상이며 구분하지 않는다.**

**구분하지 않는다는 결론만 뒤집고, 그 근거는 살린다.** §5.8이 문구 매칭을 거부한 이유는 "자동 생성 문구에 의존하면 ②를 놓친다"였고 그 지적은 옳다. 이 설계는 문구를 ①을 **골라내는** 데만 쓰고, ②는 버리지 않는다. ②의 작성자가 신입인지는 문구가 아니라 **가입일**로 판정한다.

§5.8이 몰랐던 것은 가입일을 읽을 수 있다는 사실이다. 그때는 판별 수단이 문구뿐이었고, 문구뿐이라면 구분하지 않는 쪽이 실제로 옳았다.

## 3. 실측 — 2026-08-23

`scripts/probe.mjs`로 로그인 세션을 통해 확인했다. 추측한 값은 없다.

### 3.1 HTML에는 구분 정보가 없다

`MemoList.nhn` 캡처에서 자동 생성 글과 직접 쓴 글의 항목 블록을 ID만 정규화해 비교하면, **다른 곳은 `<p class="memo-box">` 본문 텍스트 하나뿐이다.** 작성자 테이블, 회원 링크, 등급 아이콘, `AutoSourcing` 스크립트, reply-box가 모두 같다. 자동 생성 글의 작성자도 시스템이 아니라 가입한 회원 본인이라 작성자 필드로도 갈리지 않는다.

### 3.2 관리자는 그 문구를 바꿀 수 없다

`멤버 환영 관리`(`/ManageCafeJoinNotice.nhn`)의 필드는 `cafeJoinNotice.useYn`과 `cafeJoinNotice.content` 둘뿐이고, 안내문은 "입력한 내용은 멤버의 카페 가입 완료 시 환영글로 사용됩니다"다. **가입 완료 화면의 인사말이지 게시판 자동 글이 아니다.** 게시판 문구를 바꾸는 설정은 관리 메뉴 어디에도 없다.

따라서 문구 매칭이 카페 설정 변경으로 깨질 일은 없다. 네이버가 문구를 바꾸는 경우만 남고, 그것은 §5.7이 다루는 종류다.

### 3.3 가입일 엔드포인트

관리 화면의 공용 스크립트에서 `MEMBER_GETLIST` 매핑을 읽어 확정했다.

```
GET /ManageMemberListViewAjax.nhn
  ?search.clubid=<cafeId>&search.searchType=0&search.memberLevel=0
  &search.perPage=100&search.page=1&search.sortType=0&search.sortOrder=0
  &search.paginationCached=false&search.totalCountCached=0
```

응답은 UTF-8 JSON이며 `result.members[]`가 회원당 한 건이다. 쓰는 필드는 셋이다.

| 필드 | 값 | 비고 |
|---|---|---|
| `memberKey` | 43자 문자열 | 메모 게시판 작성자 키와 동일. 두 소스를 잇는 키 |
| `joinDate` | `2026.08.23.` | **KST 날짜만. 시각 없음** |
| `nickname` | 문자열 | 판별에 쓰지 않는다. §5 참조 |

`sortType=0, sortOrder=0`이 **가입일 내림차순**이다. 실제 응답이 내림차순임을 확인했다. `perPage=100`이 그대로 먹으며 100건이 약 하루치였다(`2026.08.22.`~`2026.08.23.`). 카페 전체 멤버는 209,653명이다.

### 3.4 종단 검증

가입인사 게시판 1페이지(5건)를 받아 멤버 목록과 대조했다. **5건 모두 `memberKey`로 목록에서 찾혔고 전원 당일 가입이었으며, 자동 생성 문구가 5/5 정확히 일치했다.**

### 3.5 구현 시 걸리는 것 둘

**`isSuccess`가 진짜 불리언이다.** 메모 댓글 API는 문자열 `"true"`를 주고 [`parseCommentAuthors`](../../../src/shared/automations/welcome-comment/cafe.ts)가 `String(...) !== 'true'`로 받는데, 이 엔드포인트는 JSON `true`다. 같은 카페의 두 엔드포인트가 관례가 다르니 파서를 재사용하면 안 된다.

**`memberLevelName`이 HTML 엔티티로 인코딩돼 온다**(30/30건). `nickname`은 아니었다(0/30건). 쓰는 필드가 아니라 판별에는 영향이 없지만, 나중에 이 응답에서 다른 필드를 꺼낼 때 걸린다.

## 4. 판별 규칙

가입자 목록이 유일한 근거다. `세션 실행 날짜 − 가입일 ≤ N일`이면 신입이다. `N`은 설정값이며 기본 3이다.

`joinDate`는 KST 날짜 문자열이고 `nowMs`는 UTC epoch ms다. `parse.ts`의 `KST_OFFSET_MS`를 재사용해 `nowMs`을 KST 날짜로 환산한 뒤 **일 단위로** 뺀다. `joinDate`에 시각이 없으므로 시각 단위 비교를 흉내 내면 안 된다.

글의 본문이 무엇인지(자동 생성인지, 직접 쓴 인사인지, 아니면 다른 내용인지)는 판별에 관여하지 않는다. 모든 글의 저자를 같은 기준으로 판정한다.

## 5. 가입자 표

### 5.1 판정 창을 덮는 조회

첫 실행에는 **판정 창의 바닥까지** 도달할 때까지 페이지를 역순으로 읽는다. 판정 창은 `세션 실행 날짜 − windowDays` 이전이다. 이렇게 하면 표가 판정 창 전체를 처음부터 덮고, 첫 세션 직후부터 §4의 판정이 온전히 작동한다.

이후 세션은 `page=1`부터 읽되 **이미 아는 `memberKey`를 만나면 멈춘다.** 세션 주기가 45~75분이라 그 사이 가입자는 10명 안팎이므로 평소 1페이지에서 끝난다.

멈추는 기준은 오직 데이터다 — 창 밖 가입일을 만나거나, 이미 아는 회원에 닿거나, 페이지가 빈다. 명시적 페이지 상한은 없다(조용한 잘림의 원인이 됨). 50페이지를 넘기면 경고를 남기되 멈추지 않는다.

### 5.2 "표에 없음"의 의미

표가 판정 창을 덮기 때문에(§5.1), 표에 없다는 것은 곧 **창 밖**, 즉 **도구가 보기 시작하기 전에 가입했다**는 뜻이다. 미지가 아니라 결론이다.

| 상태 | 판정 |
|---|---|
| 표에 있음, 창 안 | `세션 날짜 − 가입일 ≤ N일`이면 신입, 아니면 SKIP |
| 표에 있음, 창 밖 | SKIP |
| 표에 없음 (표가 창을 덮음) | 창 밖 → SKIP |
| 조회 실패 | 보류 (§8) |

guard에 넘기는 값은 모호한 `null`이 아니라 명시적 합집합으로 둔다.

```ts
type AuthorMembership = { kind: 'JOINED'; joinDate: string } | { kind: 'NOT_TRACKED' }
```

`existingCommentAuthors`가 `null`과 `[]`를 구분하는 것과 같은 이유다. 모르는 것과 아닌 것을 한 값에 담지 않는다.

### 5.3 저장 항목과 정리

저장하는 것은 `memberKey`(PK)와 `joinDate` 둘뿐이다. 판별에 필요한 최소이며, 로컬에 남는 개인정보도 그만큼 줄어든다. `nickname`은 조인에 쓰지 않으므로 저장하지 않는다.

`joinDate`가 `오늘 − (N+1)일`보다 오래된 행은 지운다. 표는 N일치(700~1050행)로 유지된다.

**`N`이 아니라 `N+1`인 이유.** 백로그 브레이크가 24시간이라 최대 어제 글까지 처리하는데, 어제 글의 판정에는 `어제 − N일` 가입자가 필요하다. `N`으로 자르면 그 하루치가 경계에서 사라진다.

지워진 행은 "표에 없음"이 되어 SKIP인데 N일 규칙으로도 어차피 SKIP이므로, 정리가 판정을 바꾸지 않는다.

### 5.4 문구 경로를 삭제한 이유

초판 설계(§4, 이전)는 자동 생성 글을 별도 경로로 처리해 조회 없이 통과시켰다. 근거는 "자동 생성 글의 저자는 반드시 신입"이라는 가정이었다. 그러나 워터마크 리셋이나 장시간 중단 후 재개 시 며칠 치 자동 생성 글이 축적되며, 이들이 모두 창과 무관하게 통과하는 버그가 발생했다(2026-08-23 실측).

이제 표가 판정 창 전체를 처음부터 덮기 때문에(§5.1 개선), 자동 생성 글도 다른 글과 같은 기준으로 판정할 수 있다. 문구로 특수 처리하지 않아도 항상 정확하다. 코드 단순화와 안정성 개선을 위해 경로를 삭제했다.

## 6. 프로토콜

새 메시지 한 쌍을 추가한다. `PROBE`는 진단용이므로 재사용하지 않는다.

```ts
// AppMessage
| { type: 'FETCH_MEMBERS'; requestId: string; cafeId: string; page: number; perPage: number }

// ExtensionMessage
| { type: 'MEMBERS'; requestId: string; members: RawMember[] | null }
```

`RawMember`는 `{ memberKey, joinDate }`다. `members`가 `null`이면 조회 실패이며, `COMMENTS`가 `null`로 실패를 표현하는 관례를 따른다.

게시판이 아니라 카페 단위 조회이므로 `SourceRef`가 아니라 `cafeId`를 싣는다. `SourceRef`를 쓰면 게시판 스코프라는 잘못된 인상을 준다.

## 7. 중복 환영 방지

`executions`의 유니크 인덱스는 `(cafeId, automationId, targetPostId)`다. 한 회원의 두 글은 서로 다른 글 ID라 둘 다 선점되고 댓글이 두 번 나간다.

작성자 확인을 `claim` 안으로 넣는다. 같은 카페·자동화에 같은 `target_author_id` 행이 이미 있으면 `null`을 돌려주고, [기존 `continue` 경로](../../../src/desktop/orchestrator.ts)가 그대로 처리한다. 조회와 삽입은 한 트랜잭션에 묶는다. 앱은 단일 프로세스에서 세션 루프가 순차로 돌므로 이것으로 충분하다.

`(cafe_id, automation_id, target_author_id)`에 **비유니크** 인덱스를 함께 만든다. 규칙은 `claim`이 강제하고, 인덱스는 그 조회를 받쳐줄 뿐이다. `target_author_id`는 이미 저장되고 있어 컬럼 추가는 없다.

**부분 유니크 인덱스를 쓰지 않는 이유.** 유니크 인덱스는 저장소가 규칙을 강제한다는 점에서 더 강하지만, 기존 행에 같은 작성자가 둘 이상 있으면 생성이 실패한다. 그것을 통과시키려면 중복 행을 지워야 하는데, **그 행들은 이미 댓글이 나간 `SUCCESS` 이력일 수 있다.** 규칙 하나를 위해 실행 이력을 잃는 것은 맞바꿀 만한 거래가 아니다. `authorId`가 `null`인 행끼리 충돌하지 않도록 부분 인덱스로 만들어야 하는 번거로움도 함께 사라진다.

`authorId`가 `null`이면 작성자를 특정할 수 없으므로 이 확인을 건너뛴다. 글 ID 기준 중복 방지는 그대로 남아 있다.

## 8. 보류와 워터마크

`orchestrator`는 **워터마크를 `claim`보다 먼저, 무조건 전진시킨다.** 앱이 중간에 죽어도 사이를 건너뛰지 않게 하려는 것이다. 보류는 이 순서와 맞물려야 한다.

조회에 실패한 세션에서는 작성자가 표에 없어도 그것이 "창 밖"인지 "이번에 갱신을 못 한 것"인지 알 수 없다. 그런 후보는 **이번 세션 목록에서 빼고 워터마크를 전진시키지 않는다.**

다음 세션이 같은 범위를 다시 읽고, 이미 처리된 글은 `claim`의 원자적 선점이 막는다. **재수집이 원래 안전하도록 설계돼 있어 보류가 추가 장치 없이 성립한다.**

**보류는 자동 생성 글에도 똑같이 걸린다.** 판정 근거가 가입자 목록 하나뿐이므로(§4), 목록을 못 읽으면 어떤 글도 판정할 수 없다. 조회가 실패한 세션은 한 건도 내보내지 않는다.

이것은 문구 경로를 두었을 때와 달라진 점이다. 그때는 자동 생성 글이 문구만으로 통과해 조회 실패에도 대부분 처리됐다. 근거 없이 환영하는 것보다 멈추는 편이 낫고, 보류된 글은 다음 세션이 다시 집으므로 유실이 아니며, **멈추면 눈에 띈다** — 조용히 몇 명이 빠지는 쪽이 알아차리기 훨씬 어렵다.

## 9. 모듈 배치

| 파일 | 책임 |
|---|---|
| `src/shared/members.ts` | 목록 URL 조립, 응답 파싱 |
| `src/desktop/db/membersRepo.ts` | 가입자 표 읽기·쓰기·정리 |
| `src/shared/guards.ts` | `newMemberGuard` 추가 |

멤버는 게시판이 아니라 카페 단위 개념이므로 [`cafeImage.ts`](../../../src/shared/cafeImage.ts)와 같은 층에 둔다. 가입인사 자동화 안에 넣으면 두 번째 자동화가 쓸 때 잘못된 곳에서 꺼내오게 된다.

판정은 guard로 남는다. 순수 함수이고, 정책 엔진이 SKIP 이력을 남겨 관찰이 가능하다. 보류만 워터마크를 다루는 곳에서 처리된다.

`guards.test.ts`의 경계값 두 개가 핵심이다. `joinDate`가 날짜 단위라 경계는 시각이 아니라 **날짜 차이**로만 갈린다.

## 11. 다루지 않는 것

**문구 분기.** 자동 생성 글과 직접 쓴 글에 다른 템플릿을 쓰는 것은 이번 범위가 아니다. 판별이 들어가면 가능해지지만, 필요하다는 근거가 아직 없다.

**단건 조회 폴백.** `/ManageMemberDetailInfoViewAjax.nhn`과 `/ManageMemberAutoCompleteSearchAjax.nhn`이 있는 것은 확인했으나 호출하지 않았다. 표로 충분한지 먼저 관찰한다.

**운영진 목록 자동화.** 목록 응답에 `manager`·`staff` 불리언이 있어 §5.8의 "운영진 계정 목록" 설정값을 대체할 수 있다. 중복 판정에 쓰이는 별개 관심사이므로 따로 다룬다.
