# 네이버 카페 관리 자동화 도구 — 설계

- 작성일: 2026-08-22
- 상태: 구현됨. 아래 두 절은 이후 설계가 대체했다

> **대체된 부분** — 가입인사 댓글의 대상 판정(§5.8)과 워터마크는 [안내 댓글 없는 오늘 글 설계](2026-08-23-uncommented-greetings-design.md)가 대체한다. 대상은 오늘 올라온 글 중 운영진 안내 댓글이 없는 것이고, 워터마크는 존재하지 않는다. 이 문서의 나머지는 그대로 유효하다.

## 1. 배경과 목표

네이버 카페를 소수 인원이 수동으로 운영 중이다. 반복 작업을 자동화하되, 자동화 대상을 늘려갈 수 있는 구조로 만든다.

1차 목표는 **가입인사 전용 게시판에 올라온 신규 글에 자동으로 환영 댓글을 다는 기능**이다. 다만 이 기능 하나를 위한 도구가 아니라, 자동화 작업을 플러그인처럼 추가할 수 있는 플랫폼으로 설계한다.

성공 기준:

- 운영 프로필 크롬이 켜져 있는 동안, 가입인사 게시판의 신규 글에 설정된 환영 댓글이 자동으로 달린다
- 자동화 기능마다 승인 정책(무승인 전자동 / 자동+예외승인 / 전건승인)을 개별 설정할 수 있다
- 모든 처리 이력이 기록되어 통계로 뽑을 수 있다
- 새 자동화 기능 추가 시 기존 코드를 수정하지 않는다

## 2. 비목표

- 계정 자격증명(ID/PW) 저장 및 자동 로그인 — 하지 않는다
- **세션 쿠키의 브라우저 외부 반출 — 하지 않는다.** 근거는 4.4절
- 다중 카페 동시 운영 — 1차 범위 밖
- **다중 PC 동시 운영 — 1차 범위 밖.** 단 중복 방지 계층은 인터페이스로 추상화해 확장 가능하게 둔다 (7.2절)
- 카페 페이지 오버레이 UI — 1차 범위 밖. 없어도 기능이 성립한다
- macOS/Linux 지원 — Windows 우선. 코드는 크로스 플랫폼으로 두되 검증은 Windows만
- 온라인 DB 연동 및 통계 대시보드 — Phase 6 이후, 별도 스펙

## 3. 리스크

**네이버 이용약관.** 자동화 프로그램을 통한 서비스 이용은 약관 위반 소지가 있으며, 계정 이용 제한 가능성이 실재한다. 기술로 제거할 수 있는 리스크가 아니라 운영 정책으로 관리해야 한다. 설계 전반에 총량 제한, 사람 개입 지점, 즉시 중단 장치를 기본 내장한다. 실행 계정을 카페 운영 전용 계정으로 분리해 리스크를 격리한다(4.2절).

**계정 정지 시 대응 — 사전에 정해둔다.** 정지는 기술로 막을 수 없으므로 일어났을 때의 절차를 미리 정해야 한다.

- **운영 전용 계정에 카페 매니저 권한을 주지 않는다.** 댓글 작성에 필요한 최소 등급만 부여한다. 매니저 권한까지 그 계정에 몰아두면 정지되는 순간 카페 운영 자체가 마비된다. 리스크 격리(4.2절)의 연장이다
- 정지가 확인되면 도구를 즉시 전면 정지하고(킬 스위치), 스태프 수동 운영으로 되돌린다. 도구 도입 전 상태로 돌아가는 것뿐이므로 카페 운영은 계속된다
- 이의제기 및 재개 판단은 사람이 한다. 도구가 자동으로 다른 계정으로 갈아타는 기능은 **만들지 않는다.** 그것은 제재 회피이며 상황을 악화시킨다

**네이버 오픈 API에 카페 댓글 작성 API가 없다.** 게시글 작성 위주로 제공되며 댓글은 공식 API 경로가 없다. 따라서 로그인 세션 위에서 브라우저를 통해 처리해야 한다.

**네이버 카페 DOM 및 내부 엔드포인트 변경.** 가장 빈번한 고장 원인. 대응은 5.7절 참조.

## 4. 아키텍처

### 4.1 왜 크롬 확장인가 (Playwright를 쓰지 않는 이유)

이미 로그인된 크롬 세션 위에서 동작하는 것이 요건이다. Playwright로는 달성할 수 없다.

- Chrome 정책 변경으로 기본 User Data 디렉터리 사용 중에는 `--remote-debugging-port`가 무시된다. Playwright 공식 문서도 기본 프로필 자동화를 명시적으로 경고한다(페이지 미로딩 또는 브라우저 종료).
- 프로필의 쿠키 DB를 직접 복호화하는 방식은 Windows App-Bound Encryption이 차단하며, 인포스틸러 기법이므로 채택하지 않는다.

결론: 기존 세션 위에서 동작하려면 그 브라우저 안에서 실행되는 코드여야 하고, 그것이 확장이다.

### 4.2 실행 환경 — 운영 전용 계정 + 전용 크롬 프로필

댓글을 다는 계정은 **카페 운영 전용 계정**이다. 스태프 개인 계정을 쓰지 않는다. 제재가 발생해도 개인의 메일·페이 등 다른 네이버 서비스에 영향이 없도록 리스크를 격리하기 위함이다.

네이버 세션은 브라우저당 하나이므로 개인 계정과 공존할 수 없다. 따라서 **크롬 프로필을 분리한다.**

- 스태프가 크롬에서 "운영" 프로필을 생성하고 운영 전용 계정으로 **수동 로그인**한다
- 확장은 그 프로필에만 설치한다. 개인 프로필은 영향받지 않는다
- 운영 프로필 창을 하나 띄워두면(최소화 상태 가능) 자동화가 동작한다

이는 4.1절에서 배제한 "전용 프로필" 방식과 다르다. 그것은 *자동화 도구가 프로필을 프로그램적으로 띄우는* 문제였고, 여기서는 사람이 크롬 프로필 전환 기능을 평범하게 사용할 뿐이다. Playwright 제약과 무관하며 쿠키 반출도 없다.

### 4.3 구성 요소

```
[운영 프로필 크롬 — 운영 전용 계정으로 수동 로그인됨]
        │
        │  확장 (MV3) — 판단하지 않음. 앱의 지시에만 반응
        │   · service worker: 목록 수집(fetch), 댓글 실행, WebSocket 클라이언트
        │     + chrome.alarms 재연결 하트비트 (유일한 타이머)
        │   · content script: DOM 폴백 실행 시에만 사용
        │
        │  localhost WebSocket + 토큰 페어링
        ▼
[데스크톱 앱 (Electron, 트레이 상주)]
   · 정책 엔진 (승인 정책 + 총량 게이트)
   · 승인 큐, 템플릿 편집, 기능별 설정 UI
   · 로컬 SQLite (처리 이력, 중복 방지, 통계 원본)
```

**판단과 스케줄은 전부 앱에, 수집과 실행만 확장에.** MV3 서비스 워커는 언제든 종료·재시작되므로 재시도·상태·업무 스케줄을 확장에 두면 신뢰할 수 없다. 세션을 여는 것도 앱이고(5.3절), 확장은 지시를 받아 수행하고 결과를 돌려줄 뿐이다. 서비스 워커가 죽어도 잃을 업무 상태가 없다.

**단, 확장에 타이머가 하나 필요하다 — 연결 유지용이다.** MV3 서비스 워커는 30초 유휴 시 종료된다. WebSocket 메시지 송수신은 유휴 타이머를 리셋하므로(Chrome 116+) **세션 진행 중에는 워커가 살아 있다.** 문제는 세션 사이의 45~75분이다. 이 구간에는 메시지가 없어 워커가 죽고 WebSocket도 함께 끊긴다. 앱은 죽은 워커를 깨울 수 없다.

따라서 확장은 `chrome.alarms`로 주기적으로(예: 60초) 깨어나 연결이 끊겼으면 재연결한다. 이 타이머가 하는 일은 그것뿐이며, 무엇을 언제 처리할지는 여전히 앱이 정한다.

### 4.4 세션 취급 원칙 — 쿠키는 브라우저 밖으로 나가지 않는다

확장은 `chrome.cookies` 권한을 요청하면 HttpOnly를 포함한 네이버 인증 쿠키(`NID_AUT`, `NID_SES` 등)를 읽어 앱으로 넘길 수 있다. **채택하지 않는다.** 매니페스트에 `cookies` 권한을 넣지 않는 것으로 이 원칙을 코드 수준에서 강제한다.

배제 근거:

1. **원칙 훼손** — 세션 쿠키는 2FA를 이미 통과한 상태라 유출 시 비밀번호보다 즉각적이다. 앱 메모리·디스크·로그·크래시 덤프로 노출 표면이 확장된다
2. **탐지 측면에서 오히려 불리** — 쿠키를 꺼내 Node HTTP 클라이언트로 요청하면 TLS 핑거프린트(JA3/JA4), HTTP/2 프레임 순서, 헤더 순서가 크롬과 다르다. 브라우저 안에 머무는 것이 이 시스템의 가장 큰 자산이다
3. **원래 세션 파괴 위험** — 네이버는 세션을 IP·UA 등에 바인딩한다. 불일치 감지로 세션이 무효화될 수 있다
4. **실익 부재** — 유일한 이득인 "크롬이 꺼져 있어도 동작"은 24시간 무인 운영을 뜻하는데, 이는 리스크 관리상 의도적으로 배제한 방향이다

부수적으로, 인증 쿠키를 읽어 외부로 전송하는 확장은 Chrome 웹스토어 심사에서 최소 권한 원칙 위반으로 문제가 될 소지가 크다. 비공개 배포도 심사 대상이다.

### 4.5 앱 ↔ 확장 통신

localhost WebSocket을 사용한다. Native Messaging이 크롬의 확장 ID 기반 접근 제어를 제공해 보안상 우수하나, 브라우저가 호스트 프로세스를 스폰하는 모델이라 트레이 상주 앱과 결합하려면 별도 브릿지 프로세스가 필요하다. 소수 인원 내부 도구에서 그 복잡도는 정당화되지 않는다.

로컬 프로세스 접근을 두 겹으로 막는다:

1. **토큰 페어링** — 앱이 랜덤 토큰 생성 → 트레이 UI 표시 → 확장 옵션에 1회 입력. 이후 모든 메시지에 첨부
2. **Origin 고정 (TOFU)** — 페어링 토큰을 처음으로 올바르게 제시한 확장 ID를 앱이 기록하고, 이후로는 **그 ID의 연결만 허용**한다. 다른 ID는 토큰이 맞아도 거부하며, 변경하려면 사용자가 앱에서 페어링을 명시적으로 초기화해야 한다

   확장 ID를 미리 알아야 하는 부담을 없애기 위한 방식이다. 매니페스트 `key` 필드로도 ID를 고정할 수 있으나(최초 웹스토어 업로드 시에는 `key`를 빼야 하고, 업로드 후 발급된 공개키를 넣으면 이후 고정된다) TOFU를 쓰면 그 순서에 의존하지 않는다. `key`는 개발 환경의 ID 안정성을 위해 별도로 쓴다

통신 계층은 인터페이스로 추상화하여 향후 Native Messaging 교체가 가능하도록 한다.

## 5. 자동화 모델

### 5.1 경계 — 무엇을 일반화하고 무엇을 하지 않는가

**일반화하는 것: 판단 계층.** 승인 정책, 총량 게이트, 세션 스케줄러, 상태 기계는 어떤 자동화를 돌리든 동일하게 적용된다. 자동화 종류에 따른 조건 분기(`switch`/`else if`)를 두지 않는다. 이들은 `src/shared`에 순수 함수로 두며, 자동화가 하나뿐인 지금도 그 자체로 성립한다.

**일반화하지 않는 것: 기능 모듈.** `Automation` 인터페이스를 정의하고 레지스트리에 등록하는 플러그인 구조는 **2번째 자동화가 실제로 생길 때까지 만들지 않는다.**

초안에서는 만들려 했으나 설계 리뷰에서 그 인터페이스가 2번째 기능부터 이미 맞지 않는다는 것이 드러났다.

- `Action`을 `{ cafeId, boardId, postId, body }`로 고정하면 "텍스트로 댓글 달기" 외에는 표현할 수 없다. 등업 승인/거부, 글 삭제, 정기 공지 게시는 들어가지 않는다
- `Candidate`에 글 제목·본문이 없어 스팸 판정 같은 내용 기반 자동화가 불가능하다
- 정기 공지는 감시 대상이 없어 `source`/`parse` 모델 자체가 성립하지 않는다
- 미활동 회원 정리는 전체 스캔이라 "한 페이지 → 후보들"이라는 `parse` 형태에 맞지 않는다

즉 추상화 비용은 지불하면서 그 대가로 얻으려던 확장성은 실제로 얻지 못한다. **하나의 사례에서 뽑은 인터페이스는 두 번째 사례를 만나면 대개 틀린다.** 2번째 자동화가 생기면 두 구현의 실제 공통점을 보고 추출한다.

**대신 지금 지키는 경계**

기능 모듈은 한 폴더(`src/shared/automations/welcome-comment/`)에 모으고, 평범한 함수를 내보낸다.

```ts
// 확장에서 실행 — 순수 함수라 HTML 픽스처로 테스트 가능
export function parseWelcomePosts(page: RawPage): Candidate[]

// 앱에서 실행
export const welcomeGuards: Guard[]
export function renderWelcomeComment(candidate: Candidate, template: Template): Action
```

인터페이스도 레지스트리도 없다. 판단(shared)과 수집·실행(모듈)의 경계만 지킨다. 이 경계는 인터페이스 없이도 파일 배치와 의존 방향으로 유지된다.

`Action`은 **의미 수준**으로 유지한다 — "이 글에 이 텍스트로 댓글". 엔드포인트, CSRF 토큰, DOM selector 같은 실행 세부는 확장의 실행 함수 안에 갇히고 앱은 알지 못한다.

**`Candidate`는 글 내용을 포함한다.**

```ts
interface Candidate {
  automationId, cafeId, boardId, postId
  title: string | null
  bodyText: string | null      // 치환 변수 추출과 향후 내용 기반 판정에 필요
  authorNickname, authorId, postedAt
}
```

닉네임 추출이 제목이 아닌 본문에 의존할 수 있고, 내용 없이 수집하면 나중에 다시 긁어야 한다. 수집 시점에 함께 가져오는 편이 요청 수도 적다.

### 5.2 승인 정책

세 모드의 구분 축은 **"위험 신호가 붙은 후보를 만났을 때 사람을 부르는가"** 이다.

| 정책 | 정상 후보 | 위험 신호가 붙은 후보 |
|---|---|---|
| `AUTO` 무승인 전자동 | 즉시 실행 | **스킵** 후 리포트 기록. 사람을 부르지 않음 |
| `SEMI` 자동 + 예외 승인 | 즉시 실행 | 승인 큐로 |
| `MANUAL` 전건 승인 | 승인 큐로 | 승인 큐로 (위험 표시 강조) |

`AUTO`는 "무조건 다 나간다"가 아니라 "확실한 것만 나가고 애매하면 건너뛴다"이다. 무인 운영 중 사고를 막는 핵심 규칙이다.

가입인사 자동 댓글은 대상 게시판이 전용이고 문구가 정형이므로 기본값 `AUTO`.

### 5.3 세션 모델 — 몰아서 처리하고 길게 쉰다

사람은 댓글을 균등 간격으로 달지 않는다. 앉은 김에 여러 건을 연달아 처리하고, 그다음에는 한참 손대지 않는다. 자동화도 그 리듬을 따른다. 일정한 간격으로 하루 종일 한 건씩 다는 쪽이 오히려 사람 같지 않다.

**세션** = 한 번 앉아서 처리하는 단위. 세션이 열리면 게시판을 확인하고, 처리할 건을 **연달아** 처리한 뒤 닫는다. 감지와 실행이 세션 안에서 함께 일어나므로 별도의 폴링 주기가 없다.

| 프로파일 | 세션 주기 | 세션 내 간격 | 세션당 상한 |
|---|---|---|---|
| `production` | 3~5시간 | 20~60초 | 75건 |
| `debug` | 2~4분 | 3~8초 | 5건 |

세 값 모두 매번 구간 내 균등 랜덤으로 뽑는다. 세션 내 간격이 짧은 것은 **사람이 문구를 복사해 붙여 넣는 속도**를 모사한 것이다. 15건을 처리하면 세션은 2~6분 정도 지속된다.

세션당 상한을 넘는 물량은 다음 세션으로 넘어간다. 이것도 사람의 행동과 같다 — 한 번에 다 하지 않고 나눠서 한다.

**운영 시간대 — 08:00~24:00 (설정 가능)**

이 시간대 밖에서는 세션이 열리지 않는다. 새벽 3시에 규칙적으로 환영 댓글이 달리는 것은 사람의 운영 패턴과 어긋나며 그 자체가 자동화 신호다.

**스케줄 소유권** — 세션을 여는 주체는 **앱**이다. 앱이 세션을 열어 확장에 수집을 지시하고, 판정 후 Action을 세션 내 간격에 맞춰 순차로 내려보낸다. 확장의 유일한 타이머는 WebSocket 재연결용이며 업무 스케줄과 무관하다(4.3절).

**운영 시간대 경계** — 다음 세션 예정 시각이 운영 시간대를 벗어나면 그 세션은 열지 않고, 다음 운영 시작 시각(08:00)에 첫 세션을 연다. 진행 중인 세션이 종료 시각(24:00)을 넘기면 **처리 중이던 건까지만 마치고 종료**한다. 남은 건은 다음 날 첫 세션으로 넘어간다. 세션 중간에 강제로 끊지 않는 이유는, 사람이 하던 일을 자정 정각에 칼같이 멈추지는 않기 때문이다.

**주간 편차** — 요일별로 세션 주기에 배율을 둔다(설정값). 주말은 주기를 1.5배로 늘려 활동을 줄인다. 매일 똑같은 리듬으로 도는 것 자체가 신호이기 때문이다.

**용량 산정**

운영 시간대 16시간 ÷ 평균 세션 주기 4시간 = 하루 약 4세션. 세션당 75건이면 하루 300건까지 닿을 수 있어, 가입인사 게시판 대비 **두 배의 여유**가 있다.

한 세션이 상한까지 채워도 20~60초 간격이므로 25~75분에 걸쳐 나간다. 정규 운행에서 시간당 상한 150건에 닿는 일은 없고, 상한이 실제로 무는 것은 밀린 양을 수동 실행으로 한꺼번에 메울 때다.

야간에 쌓인 40~60건은 오전 3~4세션에 걸쳐 흡수된다.

### 5.4 총량 안전장치

승인 정책과 독립적으로 항상 적용된다. 승인으로 우회되지 않는다.

- **시간당 상한** — 기본 150건. 하루 총량이 아니라 **한 시간에 나가는 양**을 잰다. 같은 200건이라도 하루에 고르게 퍼진 것과 한 시간에 몰린 것은 카페 입장에서 전혀 다른 신호이고, 눈에 띄는 쪽은 언제나 후자다. 안정적인 운행의 모습을 정한 값이지 넘으면 안 되는 위험선은 아니다
  - 집계는 **직전 60분**을 미끄러지듯 센다. 경계에서 초기화되는 구간이 없으므로 경계 앞뒤로 몰아치는 일이 생기지 않는다
  - **요청이 나간 시각으로 센다.** 지난 날을 메우는 실행도 같은 창을 쓴다 — 카페가 보는 것은 어느 날 글에 답했는지가 아니라 그 시간에 몇 번 두드렸는지다
  - **상한에 닿으면 세션만 멈추고 남은 글은 그대로 둔다.** 한 시간이 지나면 다시 대상이 되므로 종결시키지 않는다. 상한은 그 글에 대한 판정이 아니다
  - 강제 실행은 이 상한을 넘긴다(§ 강제 실행). 상한이 운행의 기준이지 절대 기준은 아니기 때문이다
- **워터마크(기준선)** — 최초 연결 시 대상 게시판의 최신 글 ID를 기준선으로 저장하고, **그보다 새로운 글만 후보로 삼는다.** 이 장치가 없으면 설치 직후 과거 글 전체가 후보가 되어 백로그 브레이크가 즉시 걸리거나 오래된 글에 댓글이 나간다
- **백로그 브레이크 (나이 기준)** — **미종결 상태**(`AWAITING_APPROVAL`, `QUEUED`, `RETRY_WAIT` — 7.1절) 후보 중 **원글 작성 시각이 24시간을 넘긴 것**이 있으면 전 모드 일시정지 후 사용자 호출. `AUTO`도 예외 없음. 종결된 건은 세지 않는다
  - 건수 기준을 쓰지 않는 이유: 일일 가입자가 100~150명이면 야간에 40~60건이 쌓이는 것이 정상이다. 건수로 재면 매일 아침 브레이크가 걸려 안전장치가 무력화된다
  - **위험한 것은 미처리가 많은 상태가 아니라 오래된 미처리가 남아 있는 상태다.** 밤새 쌓인 50건은 정상 운영이고, 5일 전 글 50건은 사고다. 총량은 시간당 상한이 이미 막고 있다
  - 승인 큐 만료(48시간)와 기준이 일관된다
- **중복 방지** — `DedupeStore.claim()`으로 글 ID를 원자적으로 선점한다. 재시작·재감지해도 중복 실행되지 않는다. 구현은 7.2절
- **세션당 상한** — 5.3절. 한 세션에서 처리할 수 있는 최대 건수
- **킬 스위치** — 트레이에서 원클릭 전면 정지. 동작을 다음과 같이 정의한다
  - 다음 세션을 열지 않는다
  - 진행 중인 요청을 `AbortController`로 즉시 취소한다
  - 아직 실행되지 않은 건은 `CANCELLED`로 확정한다
  - 취소 시점에 이미 전송이 완료된 요청의 응답은 **버리지 않고 기록한다.** 실제로 댓글이 달렸을 수 있으므로, 기록하지 않으면 다음 재개 시 중복 실행된다

### 5.5 실행 전략 — fetch 우선, DOM 폴백

`execute`는 두 전략을 순서대로 시도한다.

1. **fetch (기본)** — 확장 컨텍스트에서 `fetch(endpoint, { credentials: 'include' })`. 세션 쿠키가 브라우저에 의해 자동으로 실린다
2. **DOM 조작 (폴백)** — 1이 실패하거나 응답이 예상 형태가 아니면 페이지 조작으로 전환

fetch를 기본으로 두는 이유:

- 쿠키가 브라우저 밖으로 나가지 않는다 (4.4절 원칙 유지)
- 요청 주체가 진짜 크롬이므로 TLS 핑거프린트·헤더 순서가 완전히 일치한다
- DOM 클릭 시뮬레이션보다 안정적이고 빠르며, 마크업 변경에 덜 취약하다

DOM 폴백을 두는 이유: 카페 내부 엔드포인트는 비공개 API라 예고 없이 바뀔 수 있다. 폴백이 있으면 엔드포인트 변경 시 완전히 멈추지 않는다. CSRF 토큰 등은 페이지에서 먼저 확보해야 할 수 있으므로, `execute`는 필요한 경우 대상 페이지를 로드해 토큰을 얻은 뒤 요청한다.

`ExecutionResult`는 **어느 전략으로 성공했는지**를 함께 보고하고 앱이 이를 이력에 기록한다. fetch 실패율 상승은 엔드포인트 변경의 조기 신호이므로, 임계치를 넘으면 알림을 띄운다.

### 5.6 실패·만료·로그인 처리

**재시도** — 실행 실패 시 최대 3회. 같은 세션 안에서 즉시 재시도하지 않고 **다음 세션으로 미룬다.** 한 세션에서 같은 글에 연달아 재시도하는 것은 사람의 행동이 아니며, 실패 원인이 일시적이라면 다음 세션까지의 45~75분이 자연스러운 백오프가 된다.

재시도는 **선점을 다시 하지 않는다.** 최초 감지 때 `claim()`으로 만들어진 행이 `RETRY_WAIT` 상태로 남아 있고, 다음 세션에서 그 행을 `QUEUED`로 되돌려 처리한다. 게시판을 다시 수집했을 때 같은 글이 또 보이더라도 이미 행이 있으므로 새로 선점하지 않는다. 3회 실패 시 `FAILED`로 확정하고 알림을 띄운다. 자동 재시도는 더 하지 않는다.

**재시도 전 중복 재확인은 필수다.** 타임아웃으로 실패 처리된 요청이 실제로는 서버에 도달했을 수 있다. 재시도 직전에 해당 글의 댓글을 다시 확인해 운영진 계정의 댓글이 이미 있으면 `SKIPPED`로 종결한다.

**타임아웃 규약 — 무한 대기는 어디에도 없다**

| 대상 | 타임아웃 | 초과 시 |
|---|---|---|
| 로그인 상태 확인 | 10초 (1회 재시도) | 세션을 열지 않고 다음 세션에 재시도 |
| 목록 수집 | 15초 | 이번 세션 건너뜀. **워터마크는 갱신하지 않는다** |
| 댓글 실행 (fetch) | 15초 | 실패로 간주하고 `RETRY_WAIT` |
| 확장 응답 전반 | 20초 | 세션 중단 |

15초 상한은 임의의 값이 아니다. **MV3 서비스 워커는 응답이 30초를 넘는 `fetch`가 있으면 종료된다.** 그 절반으로 잡아 워커가 죽기 전에 우리가 먼저 끊는다.

**승인 큐 만료** — 승인 대기 상태가 48시간(설정 가능)을 넘으면 `EXPIRED`로 폐기하고 기록한다. 며칠 지난 가입인사에 뒤늦게 환영 댓글이 달리는 것은 안 다느니만 못하다.

**로그인 만료** — 매 세션 시작 시 로그인 상태를 먼저 확인한다. 미로그인이 감지되면 세션을 열지 않고 **전 자동화를 전면 정지**한 뒤 트레이 알림을 띄운다. 로그인 페이지 HTML을 게시판으로 오인해 파싱하는 사고를 막기 위함이다. 다음 세션 시점에 재로그인이 확인되면 자동으로 재개한다.

확인 자체가 실패한 경우(타임아웃, 네트워크 오류)는 **미로그인과 구분해 다룬다.** 전면 정지까지 가지 않고 그 세션만 건너뛴 뒤 다음 세션에 재시도한다. 일시적 네트워크 장애로 자동화 전체가 멈추면 복구에 사람 손이 필요해지기 때문이다. 다만 연속 3회 확인 실패 시에는 전면 정지하고 알린다.

**긴급 회수** — 잘못 나간 댓글을 되돌리는 수단이다. 파서 버그나 템플릿 실수로 다수의 댓글이 나갔을 때, 지정 구간(예: 최근 1시간, 특정 세션) 안에 도구가 작성한 댓글을 목록으로 보여주고 일괄 삭제한다. 삭제도 실행과 같은 fetch/DOM 폴백 경로를 쓴다. 삭제 결과는 `executions.deleted_at`에 기록한다. 이 기능이 없으면 200건을 사람이 하나씩 지워야 한다.

### 5.7 DOM·엔드포인트 변경 대응

selector와 엔드포인트 정의를 코드가 아닌 설정 파일로 분리한다. 네이버가 변경하면 앱 재배포 없이 설정 교체만으로 복구할 수 있다.

동시에 "구조 변경 감지"를 guard로 두어, 파싱 결과가 기대와 어긋나는 순간 해당 자동화를 정지하고 알린다. **조용히 잘못된 글에 댓글이 나가는 것보다 멈추는 것이 낫다.**

### 5.8 가입인사 모듈 명세

**대상** — 가입인사 **전용 게시판**이다. 그 게시판에 올라오는 신규 글은 전부 가입인사이므로 **제목·본문 패턴 매칭을 하지 않는다.**

| 항목 | 값 |
|---|---|
| 카페 홈 | `https://cafe.naver.com/examplecafe` |
| `clubId` | `10000000` |
| 가입인사 게시판 `menuid` | `5` |
| 게시판 형식 | **메모게시판(방명록형)** |
| 목록 주소 | `https://cafe.naver.com/MemoList.nhn?search.clubid=10000000&search.menuid=5&viewType=pc` |
| 일일 가입자 | 100~150명 |

값은 전부 설정값이며 코드에 하드코딩하지 않는다.

**게시판 형식 — 일반 글 게시판이 아니라 메모게시판이다.** 제목이 없고 본문만 있는 방명록형이며, 목록은 `MemoList.nhn`이 **서버 렌더링 HTML로 내려준다. XHR/JSON API가 아니다.** 따라서 5.5절의 "fetch 우선, DOM 폴백" 중 **fetch로 HTML을 받아 파싱하는 경로가 주 경로**가 된다. 쿠키가 브라우저 밖으로 나가지 않는다는 원칙(4.4절)은 그대로다 — 확장 컨텍스트에서 `credentials: 'include'`로 받아 확장 안에서 파싱한다.

**응답 인코딩은 UTF-8이 아니라 MS949다.** `MemoList.nhn`의 응답 헤더는 `Content-Type: text/html;charset=MS949`다(2026-08-22 DevTools 확인). `res.text()`는 UTF-8로 디코딩하므로 한글이 전부 깨진다. **반드시 `res.arrayBuffer()`로 받아 `new TextDecoder('euc-kr')`로 디코딩한다.** 요청 파라미터에 한글이 들어갈 경우도 같은 이유로 UTF-8 퍼센트 인코딩을 쓸 수 없다. 이 페이지는 jindo·jQuery 기반 구형 프론트엔드이며 `URLEncodingMap_MS949` 스크립트를 함께 로드한다.

**가입인사는 두 종류가 섞여 들어온다.** ① 네이버가 가입 시점에 자동 생성하는 글(본문이 "{닉네임}님이 우리 카페에 가입하였습니다. 댓글로 {닉네임}님을 환영해주세요."로 고정) ② 회원이 직접 쓴 인사글(예: "안녕하세요 잘부탁드립니다"). **둘 다 대상이며 구분하지 않는다.** 전용 게시판이므로 본문 패턴으로 거를 이유가 없고, 자동 생성 문구에 의존하면 ②를 놓친다.

**닉네임은 본문이 아니라 작성자 필드에서 뽑는다.** 자동 생성 글은 본문에도 닉네임이 들어 있지만 직접 쓴 글은 그렇지 않다. 작성자 필드는 두 경우 모두 존재하므로 여기가 유일하게 신뢰할 수 있는 출처다. 자동 생성 글의 작성자는 시스템이 아니라 **가입한 회원 본인**이다.

**실행 대상은 메모의 댓글이다.** 목록 상단에 새 메모를 쓰는 입력창이 있지만 도구는 그것을 쓰지 않는다. 각 메모에 달린 댓글(목록에 "댓글 N"으로 노출)이 환영 인사가 나가는 자리다.

**엔드포인트 — 실측으로 확정 (2026-08-22)**

게시판 페이지가 로드하는 자기 스크립트에서 읽어냈고, 로그인된 세션으로 실제 호출해 검증했다. 추측한 값은 없다.

| 용도 | 요청 |
|---|---|
| 목록 | `GET /MemoList.nhn?search.clubid=&search.menuid=&search.page=N&viewType=pc` |
| 댓글 조회 | `GET /MemoCommentView.nhn?search.clubid=&search.menuid=&search.articleid=&search.lastpageview=true&lcs=Y` |
| 댓글 작성 | `POST /MemoCommentPost.nhn` |
| 댓글 삭제 | `POST /MemoCommentDelete.nhn` — 긴급 회수용 |

목록은 MS949 HTML, 댓글 조회는 UTF-8 JSON이다. 한 페이지에 5건씩 실리므로 수집은 워터마크에 닿을 때까지 페이지를 거슬러 오른다. 로그인 여부와 실행 계정은 게시판 페이지의 `g_sUserId`·`g_sUserMemberKey`로 판정한다 — 카페 대문이 아니라 게시판을 읽으므로 세션이 살아 있는지와 이 게시판에 접근 가능한지를 한 번에 확인한다.

**작성 요청은 Referer를 요구한다.** 댓글 폼에는 CSRF 토큰이 없고, 서버가 위조 요청을 거르는 수단은 Referer뿐이다. 헤더 없이 보내면 **200을 응답하면서 아무 일도 하지 않는다.** 게시판은 페이지 안의 숨은 폼을 iframe으로 제출하므로 이 헤더가 자연히 실리지만, 확장의 `fetch`는 실을 수 없다(금지 헤더). 따라서 `declarativeNetRequest` 세션 규칙으로 그 요청 직전에만 `Referer`/`Origin`을 게시판 페이지로 세팅하고 끝나면 즉시 제거한다. 권한은 `declarativeNetRequestWithHostAccess`로 제한해 이미 가진 host_permissions 범위를 넘지 않는다.

**성공 판정은 응답이 아니라 재조회로 한다.** 이 엔드포인트는 숨은 iframe용 페이지를 돌려주므로 200이 성공을 뜻하지 않는다. 작성 후 댓글을 다시 읽어 실행 계정의 `memberKey`가 보일 때만 성공으로 기록한다. 타임아웃으로 실패 처리된 요청이 실제로는 도달한 경우(5.6절)도 이 방식이면 정확히 판정된다.

**추출 항목** — 글 ID, 작성자 닉네임, 작성자 회원 ID, 작성 시각.

**댓글 문구** — 템플릿을 N개 등록한다. **N=1이면 그 문구를 쓰고, N≥2이면 매번 균등 랜덤으로 고른다.** 별도의 모드 설정을 두지 않고 등록 개수로 동작이 결정된다. 사용 가능한 치환 변수는 `{닉네임}`이다.

**실행 계정 식별** — 확장이 카페 페이지에서 현재 로그인 회원 정보를 읽어 앱에 전달한다. 앱은 모든 이력에 실행 계정을 함께 기록한다.

**운영진 계정 목록** — 중복 판정에 쓰는 설정값이다. 운영 전용 계정과 스태프 개인 계정들을 등록한다. 이 목록 중 누군가의 댓글이 이미 달려 있으면 도구는 손대지 않는다.

**guards**

- 닉네임 등 치환 변수 추출 실패
- 해당 글에 이미 **운영진 계정 목록**(설정값) 중 하나의 댓글이 존재 → 위험 신호가 아닌 **스킵** 처리. 실행 계정 하나만 보면 스태프가 개인 계정으로 먼저 환영 댓글을 단 글에 도구가 또 다는 사고가 난다. 특히 Phase 5 램프업 기간처럼 사람과 도구가 같은 게시판을 나눠 처리할 때 실제로 발생한다
  - **판정은 로컬 DB가 아니라 네이버에서 재조회한다.** 로컬 DB는 도구가 단 댓글만 알고 스태프가 수동으로 단 것은 모른다
  - **확인 시점과 실행 시점 사이에 경합이 있다.** 수집 시점에 댓글이 없었어도 실행 직전에 스태프가 달 수 있다. 따라서 **실행 직전에 한 번 더 확인**한다. 세션 내 간격이 8~25초이므로 이 창은 짧지만 0은 아니다
  - 재조회가 타임아웃되면 "확인 불가"로 보고 위험 신호를 붙인다. 확인하지 못한 채 다는 것보다 사람에게 넘기는 편이 낫다
- 게시판 구조 변경 감지
- fetch 엔드포인트 응답이 예상 형태와 불일치 → DOM 폴백으로 전환하고 알림

## 6. 데이터 흐름

```
앱    세션 개시 (운영 시간대 확인 → 세션 주기 대기 만료) → 확장에 수집 지시
  ↓ WebSocket
확장   로그인 상태 확인 → 워터마크 이후 신규 글 목록 수집 → 회신
  ↓ WebSocket
앱    후보별로:
      1. DedupeStore.claim() — 원자적 선점. 실패 시 중단
      2. guards 평가 → 위험 플래그 산출
      3. 총량 게이트 (시간당 상한 / 세션당 상한 / 백로그 브레이크 / 킬 스위치)
      4. 승인 정책 적용 (AUTO / SEMI / MANUAL)
      5. 템플릿 선택 + 렌더링 → Action 생성
      → 실행 대상들을 세션 내 간격(20~60초)으로 순차 전달
  ↓ WebSocket
확장   execute — fetch 시도 → 실패 시 DOM 폴백 → 결과 회신
  ↓
앱    이력 확정 (SUCCESS / FAILED / SKIPPED / EXPIRED + 사유 + 사용 전략) → 세션 종료
```

1~5단계는 전부 순수 함수로 구현한다. 브라우저·DB·네이버 없이 단위 테스트로 전부 검증 가능하다는 점이 이 설계에서 가장 중요하다.

## 7. 데이터 모델

### 7.1 테이블

승인 큐를 별도 테이블로 두지 않는다. 한 글의 생애를 `executions` 한 행에 담고 `status`로 상태를 전이시킨다. 그래야 통계를 한 곳에서 뽑을 수 있고 큐와 이력이 어긋날 여지가 없다.

```
executions                       -- 한 글 = 한 행. 중복 방지와 통계의 단일 원천
  id                TEXT PK
  automation_id     TEXT         -- 'cafe-welcome-comment'
  cafe_id           TEXT
  board_id          TEXT
  target_post_id    TEXT         -- 네이버 글 ID
  target_author     TEXT         -- 가입인사 작성자 닉네임
  target_author_id  TEXT
  target_posted_at  INTEGER      -- 원글 작성 시각
  actor_account     TEXT         -- 실행 계정
  status            TEXT         -- 아래 상태 기계 참조
  strategy          TEXT         -- FETCH | DOM | NULL
  risk_flags        TEXT         -- JSON 배열
  reason            TEXT         -- 스킵·실패·만료 사유
  template_id       TEXT
  rendered_text     TEXT         -- 실제로 나간 텍스트
  target_title      TEXT         -- 원글 제목
  attempts          INTEGER      -- 실행 시도 횟수. 최초 0
  detected_at       INTEGER      -- 감지·선점 시각
  executed_at       INTEGER      -- 실제 실행을 시도한 시각. 시도 전이면 NULL
  resolved_at       INTEGER      -- 종결 상태로 확정된 시각. 미종결이면 NULL
  deleted_at        INTEGER      -- 긴급 회수로 삭제한 시각 (5.6절)
  UNIQUE (cafe_id, automation_id, target_post_id)   -- 중복 방지의 실체

templates
  id, automation_id, body, enabled, created_at

automation_settings
  automation_id PK, policy, limits(JSON), enabled

watermarks
  (automation_id, board_id) PK, last_seen_post_id, updated_at

app_settings
  key PK, value                  -- 프로파일, 페어링 토큰, 카페/게시판 ID 등
```

**상태 기계**

`PENDING` 하나로 승인 대기·실행 대기·재시도 대기를 뭉개면 UI에서 구분할 수 없고 백로그 브레이크가 무엇을 세야 하는지도 모호해진다. 셋을 분리한다.

```
       감지 → claim() 성공 → 행 생성
                  │
                  ├─→ SKIPPED             (이미 운영진 댓글 있음 등. 종결)
                  ├─→ AWAITING_APPROVAL   (MANUAL 전건, 또는 SEMI에서 위험 신호)
                  └─→ QUEUED              (자동 승인)

  AWAITING_APPROVAL ─ 사람이 승인 ─→ QUEUED
                    ─ 사람이 거부 ─→ SKIPPED        (종결)
                    ─ 48시간 경과 ─→ EXPIRED        (종결)

  QUEUED ─ 실행 성공 ──────────────→ SUCCESS        (종결)
         ─ 실행 실패, 시도 < 3 ────→ RETRY_WAIT
         ─ 실행 실패, 시도 = 3 ────→ FAILED         (종결)
         ─ 킬 스위치 ─────────────→ CANCELLED      (종결)

  RETRY_WAIT ─ 다음 세션 ──────────→ QUEUED
```

**미종결 상태는 `AWAITING_APPROVAL`, `QUEUED`, `RETRY_WAIT` 셋뿐이다.** 백로그 브레이크(5.4절)가 세는 대상이 바로 이 셋이다. `resolved_at`은 종결 상태로 확정될 때 설정되며, 미종결 상태에서는 `NULL`이다.

`strategy`는 실행을 실제로 시도한 경우에만 채워진다. `SKIPPED`, `EXPIRED`, `AWAITING_APPROVAL`에서는 `NULL`이다.

`reason`은 자유 텍스트가 아니라 **enum**이다(`ALREADY_COMMENTED`, `VARIABLE_EXTRACTION_FAILED`, `APPROVAL_TIMEOUT`, `KILLED`, `ENDPOINT_MISMATCH` 등). 통계 집계의 축이 되므로 자유 텍스트면 쓸모가 없다.

이 한 테이블에서 나오는 통계: 일별·주별 처리량, 성공률, `FETCH`/`DOM` 전략 비율(엔드포인트 건강도), 스킵·실패 사유 분포, 계정별 집계, `target_posted_at → executed_at` 차이로 **응답 지연**, `executed_at` 분포로 **시간대별 처리량**.

`resolved_at`만으로는 실제 실행 시점을 알 수 없다. 승인 대기나 재시도를 거치면 종결 시각과 실행 시각이 크게 벌어지기 때문에 둘을 따로 기록한다.

### 7.2 중복 방지 계층

1차는 단일 PC 운영이므로 로컬 SQLite로 충분하다. 다만 나중에 여러 PC로 확장할 때 설계를 갈아엎지 않도록 인터페이스로 감싼다.

```ts
interface DedupeStore {
  claim(automationId: string, postId: string): Promise<boolean>  // 원자적 선점
}
```

선점 키에 `cafe_id`가 들어가는 것이 중요하다. 카페마다 글 ID가 독립적으로 매겨지므로, 빼면 카페 A의 1001번 글과 카페 B의 1001번 글이 같은 글로 취급된다. 다중 카페는 1차 범위 밖이지만 이 제약을 나중에 바꾸려면 데이터 마이그레이션이 필요하므로 지금 넣는다.

`claim`이 "확인 후 기록"이 아니라 **원자적 선점**인 것이 핵심이다. 로컬 구현은 `UNIQUE` 제약 위반을 `false`로 변환하면 되고, 공유 저장소로 갈 때도 같은 의미가 성립한다. 이 인터페이스만 지키면 다중 PC 확장은 구현체 교체로 끝난다.

**선점은 "이 글을 우리가 맡는다"이지 "처리를 끝냈다"가 아니다.** 선점에 성공하면 행이 생기고, 이후의 승인·실행·재시도는 전부 그 행의 상태 전이로 다룬다. 재시도할 때 `claim`을 다시 부르지 않는다. 게시판을 다시 수집해 같은 글이 또 보이더라도 `claim`이 `false`를 반환하므로 새 행이 생기지 않으며, 이는 정상 동작이다.

이 구분이 없으면 재시도가 영원히 불가능해진다. 실패한 건이 다음 세션에서 재감지될 때 `claim`이 막고, 그 행을 되살릴 경로가 없기 때문이다.

| 확장 배포 | Chrome 웹스토어 비공개(unlisted) | 개발자 등록 5달러 일회성. 자동 업데이트가 따라오고, 개발자 모드 압축 해제 로드의 경고 팝업과 수동 배포를 피할 수 있다 |

## 9. 프로젝트 구조

**단일 패키지다.** pnpm 워크스페이스도, 패키지 분할도 두지 않는다.

```
whisky-manager/
├── package.json          하나
├── tsconfig.json         타입체크 (src + tests)
├── tsconfig.build.json   데스크톱 빌드 (src/extension 제외)
├── vitest.config.ts
├── src/
│   ├── shared/           순수 TS — 타입, 포트, 스케줄러, 게이트, guards, 정책, 상태 기계, 프로토콜
│   │   └── automations/welcome-comment/   기능 모듈 (5.1절)
│   ├── desktop/          Electron 메인 — DB, WS 서버, 오케스트레이터, 트레이, 렌더러
│   └── extension/        MV3 — service worker(수집/실행/WS), content script(DOM 폴백)
└── tests/
    ├── shared/
    ├── desktop/
    └── extension/
```

**왜 나누지 않는가.** 초안은 패키지 5개(core / protocol / automations / desktop / extension)로 나눴다. 소수 인원이 유지보수한다는 명시적 요구에 비추면 그 대가가 이득보다 크다 — package.json 5개, tsconfig 5개, 패키지 간 빌드 순서 의존, 테스트에서 소스를 참조하기 위한 별칭 우회. 실제로 초안 계획서는 그 별칭 우회를 이미 필요로 했다.

패키지 경계가 주는 강제력은 나중에 이 코드를 외부에 배포할 때 의미가 생긴다. 사내 도구에는 그런 계기가 없다.

**의존 방향은 폴더 배치로 지킨다**

- `src/shared`는 Electron·브라우저·DB 어디에도 의존하지 않는다. 앱과 확장 양쪽이 임포트하므로 **Node 전용 모듈(`better-sqlite3` 등)과 브라우저 전용 API를 모두 배제한다.** 이 경계가 무너지면 테스트 전략 전체가 무너지고, 네이티브 모듈이 확장 번들로 끌려 들어간다
- `src/desktop`은 `src/shared`를 임포트한다. 반대 방향은 없다
- `src/extension`은 `src/shared`를 임포트한다. `src/desktop`은 임포트하지 않는다
- 임포트는 상대 경로를 쓴다. 경로 별칭을 두면 tsc·vite·vitest 세 곳에 같은 설정을 중복해야 한다

공유 타입(`Candidate`, `Action`, `ExecutionResult`, `RawPage`, `GuardContext`, `Limits`, `Template`, `RiskFlag`)의 구체 정의는 구현 계획 단계에서 `src/shared`에 확정한다. 이 스펙은 각 타입의 역할과 실행 위치까지만 규정한다.

## 10. 테스트 전략

- **정책 엔진** — Vitest 단위 테스트. 순수 함수이므로 전 분기 커버 가능. 커버리지 80% 이상
- **세션 스케줄러** — 가짜 시계로 검증: 운영 시간대 밖에서 세션이 열리지 않는지, 세션당 상한 초과분이 다음 세션으로 넘어가는지, 세션 주기·세션 내 간격의 지터 분포가 구간 안에 있는지
- **총량 게이트** — 워터마크, 시간당 상한에 닿았을 때 세션이 멈추는지, 나이 기준 백로그 브레이크를 가짜 시계로 검증
- **중복 방지** — `claim` 동시 호출 시 정확히 하나만 `true`를 받는지 검증
- **DOM 파서** — 실제 카페 페이지 HTML을 픽스처로 저장하고 파싱 결과를 검증. 네이버가 마크업을 변경하면 이 테스트가 먼저 깨져 조기 경보 역할을 한다
- **실행 전략** — 목 서버로 fetch 성공 / fetch 실패 → DOM 폴백 전환 / 양쪽 모두 실패 세 경로를 모두 검증. `ExecutionResult`가 사용된 전략을 정확히 보고하는지 확인
- **로그인 만료** — 로그인 페이지 HTML을 던졌을 때 파싱하지 않고 전면 정지하는지 검증. 확인 실패(타임아웃)와 미로그인을 구분해 다루는지, 연속 3회 실패에서 전면 정지하는지도 함께 검증
- **상태 기계** — 7.1절의 모든 전이를 검증. 특히 `QUEUED → RETRY_WAIT → QUEUED` 경로에서 `claim`을 다시 호출하지 않는지, 3회 실패가 `FAILED`로 종결되는지
- **타임아웃** — 모든 외부 호출이 규정된 시간 안에 끊기는지. 응답을 영원히 주지 않는 목 서버로 검증
- **킬 스위치** — 세션 진행 중 발동 시 진행 중 요청이 취소되고 미실행분이 `CANCELLED`로 확정되는지. 전송 완료된 요청의 응답이 버려지지 않고 기록되는지
- **중복 경합** — 확인 시점과 실행 시점 사이에 댓글이 생기는 상황을 목 서버로 재현해, 실행 직전 재확인이 이를 잡아내는지
- **통합** — 카페를 모사한 로컬 목 페이지를 띄우고 Playwright로 확장을 로드해 검증
- **실계정 대상 자동 E2E는 만들지 않는다.** 반복 실행 자체가 리스크다

## 11. 단계 계획

| Phase | 내용 | 완료 기준 |
|---|---|---|
| 0 | 단일 패키지 스캐폴딩, TS/ESLint/Vitest 설정 | `pnpm build`, `pnpm test`, `pnpm lint`, `pnpm typecheck` 통과 |
| 1 | `src/shared` — 정책 엔진, guards, 총량 게이트, 워터마크 | 단위 테스트 커버리지 80%+. UI·DB·브라우저 없이 전부 검증 |
| 2 | 프로토콜 + WS 페어링 + SQLite 스키마/마이그레이션 + `DedupeStore` | 확장 스텁과 앱이 왕복 통신, 이력이 DB에 기록됨, `claim` 동시성 테스트 통과 |
| 3 | 엔드포인트 확정(DevTools 관찰) → 가입인사 모듈 수집·파서 + 댓글 실행(fetch/DOM 폴백) + 로그인 만료 감지 | 실제 응답 픽스처로 파서 테스트 통과, 실행 전략 3경로 통과, 로컬 목 페이지 통합 테스트 통과 |
| 4 | 데스크톱 UI — 대시보드, 승인 큐, 기능별 정책 설정, 템플릿 편집, 긴급 회수 | 세 정책 모드 전환이 실제로 동작, 긴급 회수로 지정 구간 댓글이 실제 삭제됨 |
| 5 | 배포 — CWS 비공개 등록, electron-updater, Windows 인스톨러 | 스태프 PC 설치 후 소량 실계정 검증 |
| 6+ | 온라인 DB 동기화 + 통계 대시보드 + 다중 PC | 별도 스펙 |

**Phase 5 램프업**

일일 가입자가 100~150명이므로, 검증 기간에도 카페 운영은 멈출 수 없다. 도구가 일부를 맡고 **나머지는 스태프가 평소대로 수동 처리**하는 병행 운영으로 간다. 중복은 운영진 계정 목록 guard가 막는다.

| 단계 | 최소 기간 | 정책 | 시간당 상한 | 다음 단계 진출 조건 |
|---|---|---|---|---|
| 1 | 3일 | `MANUAL` | 10건 | 3일 연속 나간 댓글 전수 확인에서 부적절 건 0. `FAILED` 0 |
| 2 | 7일 | `SEMI` | 50건 | 위험 신호 오탐률 10% 미만. 승인 큐 만료(`EXPIRED`) 0 |
| 3 | — | `AUTO` | 150건 | — |

진출 조건을 못 채우면 기간을 연장한다. 기간이 차는 것만으로 넘어가지 않는다.

램프업 중 도구가 처리하지 못한 건은 상한에 걸려 행조차 남기지 않고 지나가며, 사람이 담당한다. 백로그 브레이크는 미종결 상태만 세므로(7.1절) 이 상황에서 오탐이 나지 않는다.

## 12. Phase 6로 미룬 결정

온라인 DB는 Supabase(Auth + RLS 내장으로 스태프별 권한이 바로 해결)와 Neon(Postgres만, 인증은 직접 구현) 사이의 선택이다. 통계 요건이 구체화되기 전에 정하면 틀리기 쉬우므로 Phase 6 별도 스펙에서 결정한다.

다중 PC 운영도 같은 시점에 다룬다. `DedupeStore` 구현체를 공유 저장소로 교체하는 것이 핵심이며, 인터페이스는 이미 7.2절에 정의되어 있다.
